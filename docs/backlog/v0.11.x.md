# v0.11.x: Connector Foundations

For strategic overview, see the [planning overview](README.md).

## User Workflow Context

The user's musical life spans more services than mixd can see: Apple Music and Tidal are invisible to the play history and library v0.10.x made honest, and the physical collection catalogued on Discogs has no presence. The existing Spotify connector also has to track Spotify's 2026 program changes to stay trustworthy. This cycle lands the *bones* of three connectors — auth, API clients, conservative track resolution, the Apple play channel — plus a Spotify currency pass. It deliberately precedes first-class artists and albums (v0.12.x) for two reasons: entity modeling should be designed against real catalog data from six services (the v0.12.0 spike consumes these clients), and Apple plays should start accruing into the observation ledger now rather than after the entity work. Full feature surfaces — Apple library/likes, Discogs collection import, Tidal likes/playlists — intentionally wait for v0.13.x, once the entities they attach to exist.

Persona view (from the [alignment table](README.md#persona-alignment)): the **Weekly Curator** gets Apple listening flowing into their canonical history and a Spotify connection that asks to reconnect instead of failing silently; the **Tinkerer** gets three new connectors' raw surfaces to poke at; the **Casual** listener gets the groundwork for "connect Apple Music" and "connect Tidal" being first-class buttons.

Cross-cutting contract (stated once — per-epic Specs reference it): every new use case this cycle must be classified in the chat-tool parity registry (`src/application/tools/registry.py`) — CI (`tests/unit/application/tools/test_registry_parity.py`) fails on any unclassified use case. Reads get a `ToolSpec` or an explicit classification; mutations additionally get two-phase confirmation wiring like the existing `*_write` dispatchers.

### v0.11.0: Apple Music Foundation

**Goal**: mixd can authenticate to Apple Music, resolve its tracks conservatively, and capture Apple plays as a live observation channel — the bones that let the v0.12.0 spike see Apple's real catalog shapes and let play history start accruing immediately.

**Context**: An existing stub at `src/infrastructure/connectors/apple_music/` (`connector.py`, `error_classifier.py`) provides the starting point; shared infrastructure (`_shared/http_client.py`, retry policies, error classification) means the client is mostly wiring. Auth differs from Spotify in kind, not degree. The developer token is a self-signed ES256 JWT (Team ID, `kid`, `exp` ≤6 months). The per-user Music User Token (MUT) exists **only** via MusicKit JS `authorize()` in a browser — Apple offers no server-side user auth and no CLI path. The MUT lives 6 months, fixed, with no refresh ([Apple staff](https://developer.apple.com/forums/thread/654814)). **Doctrine: each deployment brings its own Apple Developer membership (US$99/yr)** and pastes its `team_id`/`key_id`/`.p8` key into instance config; this deployment's membership is in place. Apple has no "love" API (Add to Library is the like analogue — deferred with the rest of the library surface to v0.13.0). Play data accrues only once the user actually listens on Apple Music; the channel ships regardless so nothing is lost when they do. Endpoint reference: [provider-integration-research-2026-08.md](provider-integration-research-2026-08.md).

**What this unlocks**: Apple catalog access for the v0.12.0 entity-representation spike; Apple plays flowing through the v0.10.0 projection; the auth substrate v0.13.0's library/likes integration reuses.

**Persona**: Curator-primary (Apple listening joins the canonical history); Tinkerer secondary (a fourth connector's auth model to inspect).

**Key Design Decisions**:
- **Ingest early, resolve conservatively** — Apple observations land in `connector_plays` immediately, but resolution is **ISRC-only** (excellent coverage in Apple's catalog); fallback candidates are recorded *unresolved* rather than matched, because the pre-alias comparator (alias-aware artist comparison lands in v0.12.1) would mint permanent weak mappings. v0.13.0's re-resolution pass + `mixd plays rebuild` promotes the deferred observations once the full matcher exists. No permanent weak mappings, no lost plays.
- **Supersession-native from birth** — landing after v0.10.2 means Apple's platform-asserted succession (`catalogId` vs `playParams.catalogId` equivalence, parallel to Spotify relinking) is representable in the mapping schema from the first row; the migration the old sequencing risked never happens.
- **The play channel is presence-weak by design** — Apple's recently-played API returns **no timestamps** (≤30 items, offset paging), so `played_at` is approximated from the poll window with a channel-specific wide tolerance, and the `apple_api` channel ranks below every timestamped channel in survivorship: it may create a play, but never wins timestamp fields against an observer that knows when.

#### Substrate Epics (cycle-wide)

- [ ] **Connector Auth-State Fidelity**

    **Story**: The user whose connector credential ages out wants the app to say "reconnect", not fail silently or show a generic error. Two of this cycle's credentials expire by design — the Spotify refresh grant (v0.11.2 Context) and the Apple MUT (v0.11.0 Context) — so "credential expired, reconnect" must be a first-class state every connector can raise.

    **Decisions**:
    - **Expected expiry is a state, not an error** — the user can fix it in one click, and an error-styled surface trains them to ignore real failures.
    - **No `StoredToken` schema change** — `total=False` plus `extra_data` (JSONB) already absorb every credential shape this cycle adds; a documented field contract prevents per-connector drift.

    **Spec**:
    - Add `"reauth_required"` to `ConnectorAuthError` (`src/domain/entities/connector.py:34`); map it in `derive_status_state()` (:76) to `"needs_reauth"` (the `scope_missing` branch is the pattern)
    - Widen `ConnectorAuthMethod` (:20) once for the auth shapes this cycle adds (browser-bridge, personal access token, device-code); pick the exact literals at implementation
    - Document the per-connector `StoredToken` field contract in `_shared/token_storage.py`'s docstring: Apple = opaque `access_token` + explicit `expires_at`, no `refresh_token`; Tidal = access + refresh pair; Discogs = personal access token (OAuth 1.0a token secret in `extra_data` if ever needed); `authorized_at` (Unix ts) in `extra_data` wherever grant age matters
    - Web (`GET /connectors`) and CLI status render `needs_reauth` with a reconnect affordance (surfaces exist — `_shared/connector_status.py`, `interface/cli/connector_commands.py`)

    **Tests**:
    - (unit) `reauth_required` → `derive_status_state()` returns `needs_reauth`
    - (integration) the web connector list and CLI status render the reconnect state, not an error

    Effort: S | Dependencies: None | Status: Not Started

#### Apple Foundation Epics

- [ ] **Apple Music Auth & API Client**

    **Story**: Every Apple Music operation — catalog lookups for the spike, play polling, the eventual library sync — needs an authenticated client; this is the connector's foundation and the external-prerequisite resolver for everything Apple.

    **Decisions**:
    - **Developer token minted server-side; user token only via the MusicKit JS browser bridge** — Apple offers no server-side user auth, so the connector is web-only by construction. The CLI reads Apple data through the server but can never mint a MUT.
    - **Persist the MUT server-side** (encrypted, RLS-scoped, explicit `expires_at`) — MusicKit's own per-origin browser storage silently de-authorizes when the instance is reached at a second hostname ([music-assistant #3897](https://github.com/orgs/music-assistant/discussions/3897)).

    **Spec**:
    - `AppleMusicAPIClient(BaseAPIClient)` with httpx2; Pydantic models for JSON:API response shapes; rebuild the pre-modern `apple_music/` stub to the current spotify/lastfm package layout
    - Developer token: ES256 mint from instance config (`team_id`, `key_id`, `.p8` key), `exp` ≤6 months, rotate ~90 days (starting point, revisit), cached until expiry; optional `origin` claim as an admin hardening field — the claim is developer-authored, no Apple-side registration exists
    - Bridge route: loads MusicKit JS v3 from Apple's CDN (it cannot be vendored), runs `authorize()`, POSTs the resulting MUT to the backend; the route sets `Referrer-Policy: strict-origin-when-cross-origin` — a stricter policy (e.g. `no-referrer`) is the documented cause of `authorize()` 403s
    - MUT storage via the `TokenStorage` pattern (encrypted at rest), `expires_at = granted_at + 6 months`, no refresh; a 403 `TOKEN_EXPIRED` raises `reauth_required` and the connector card offers re-authorize
    - Refactor existing `AppleMusicErrorClassifier` to the modern hook pattern
    - Reuse: `_shared/http_client.py`, `_shared/retry_policies.py`, `_shared/error_classifier.py`

    **Tests**:
    - (unit) developer-token mint/expiry/cache — correct ES256 claims; the key never serializes into a response
    - (integration, mocked transport) 401 → actionable reconnect error; retry policy on 5xx
    - (integration) expired MUT (403 `TOKEN_EXPIRED`) yields `needs_reauth`, not a generic error
    - (integration) the bridge route response carries the `Referrer-Policy` header

    Effort: L | Dependencies: Connector Auth-State Fidelity (Apple Developer membership in place) | Status: Not Started

- [ ] **Conservative Track Resolution**

    **Story**: Apple tracks must connect to canonical tracks for plays and the spike to mean anything — but mappings are permanent until v0.10.2's supersession machinery is exercised, so the resolver must only assert what it can anchor.

    **Decisions**:
    - **ISRC-first, ISRC-only** — no artist+title fallback in this milestone: the alias-aware comparator doesn't exist until v0.12.1, and a weak mapping minted now persists. Fallback candidates are recorded as unresolved observations and queued via the v0.10.2 event log's no-match backoff — v0.13.0's "Deferred Play Re-Resolution" epic is their designed exit.
    - **Content equivalence via dual mapping** — `catalogId` vs `playParams.catalogId` reuses the Spotify-relinking dual-mapping pattern, recorded as platform-asserted succession (v0.10.2 typed reason).

    **Spec**:
    - `AppleMusicInwardResolver` + `AppleMusicMatchingProvider` with only the ISRC path active
    - `filter[isrc]` batches ≤25 identifiers per request; every catalog path is storefront-scoped — read the user's storefront once via `GET /v1/me/storefront` (needs the MUT) and hold it as connection state
    - `filter[equivalents]` is the cross-storefront successor surface behind the dual-mapping decision
    - Reuse: `_shared/inward_track_resolver.py`, `_shared/matching_provider.py`, `_shared/isrc.py` (including the ISRC-suspect duration cross-check)
    - Unresolved-candidate recording: ledger rows keep `resolved_track_id = NULL`; no-match rows enter the v0.10.2 backoff queue

    **Tests**:
    - (unit) ISRC hit → mapping with `match_method="isrc"`; no ISRC → **no** `artist_title` mapping minted, observation stays unresolved
    - (integration) unresolved Apple ledger rows excluded from the projection and queryable for the v0.13.0 re-resolution pass

    Effort: M | Dependencies: Apple Music Auth & API Client, v0.10.2 (supersession schema) | Status: Not Started

- [ ] **Apple Play Channel**

    **Story**: The Apple Music listener's plays should land in the same canonical history as everything else — this activates the channel the v0.10.0 projection was designed to accept without new dedup code (that claim is this epic's acceptance test).

    **Decisions**:
    - **Poll-window-midpoint timestamps, presence-only precedence** — Apple returns no `played_at`, so the channel contributes *that* a play happened, never *when* precisely; the projection's channel-keyed survivorship handles the rest.
    - **Rides the v0.10.1 polling policy wholesale** — demand triggers, adaptive heartbeat, redundancy-aware caps, and the shared `run_sync_target` runner all apply; Apple is one more `SYNC_TARGETS` entry and one more checkpoint row, not new infrastructure.

    **Spec**:
    - Client: `GET /v1/me/recent/played/tracks` (`types=songs`, window ≈30 items — community-measured 2021–23, measure at implementation; offset paging)
    - Channel `("apple", "apple_api")`: identifier = Apple catalog song id; `played_at` = poll-window midpoint; channel-specific wide tolerance constant in `play_projection.py`; lowest timestamp-precedence rank
    - `SYNC_TARGETS["apple:plays"]` (`SyncTargetSpec`, `src/application/use_cases/_shared/sync_targets.py`), executed by `run_sync_target` (`src/application/services/sync_target_runner.py`); add `("apple", "plays")` to `CHECKPOINT_COMBINATIONS` (`sync_likes.py`) so the sync-status table shows the checkpoint with effective-interval-aware staleness
    - Rate posture: Apple publishes no limits and returns no rate headers; 429s self-resolve; the quota attaches to the developer token, so every user of the instance shares one budget
    - Import stats + `OperationRun` audit come free from the shared runner

    **Tests**:
    - (unit) wide-tolerance grouping + presence-only survivorship for `apple_api` observations
    - (integration) simulated overlapping Apple + Last.fm observations of one listen → one canonical play, Last.fm's timestamp wins
    - (manual — milestone acceptance) connect Apple → listen → play appears in history and the sync table shows the checkpoint row

    Effort: M | Dependencies: Conservative Track Resolution, v0.10.1 (polling infrastructure) | Status: Not Started

### v0.11.1: Discogs Foundation

**Goal**: An authenticated Discogs client and a first look at the user's collection — the bones the v0.12.0 spike queries and v0.13.1 physical media builds on.

**Context**: Discogs has 15M+ releases with the richest physical-media metadata anywhere (formats, labels, catalog numbers, pressing notes) and a distinctive artist model (name variations, ANVs, join phrases) that the v0.12.0 spike must see before artist entities are designed. The user's own collection may still be small or empty — the snapshot degrades gracefully, and the *catalog* endpoints (release/master/artist) are what the spike consumes regardless.

**What this unlocks**: Discogs catalog access for the spike; the client and token plumbing v0.13.1's collection import reuses; the connector-card presence that invites the user to start cataloguing.

**Persona**: Curator-primary (the record collector's on-ramp); Tinkerer secondary.

**Key Design Decisions**:
- **Foundations only** — no canonical writes this milestone: release matching and collection import need albums (v0.12.2) and land in v0.13.1; shipping the client early is what makes the spike's Discogs leg real instead of speculative.

#### Discogs Foundation Epics

- [ ] **Discogs API Client & Auth**

    **Story**: Every Discogs operation — collection import, release detail — needs an authenticated client; this is the connector foundation.

    **Decisions**:
    - **Per-user personal access token (BYO-token), not OAuth 1.0a** *(2026-07 check: Discogs API healthy, no deprecation; tokens officially recommended for single-user apps — same 60 req/min, never expire)* — collection reads don't need the OAuth dance, and BYO-token matches the existing BYO-Anthropic-key pattern (v0.9.0.1): validated live, stored encrypted, write-only in the UI. The client takes an injected auth strategy so OAuth 1.0a can slot in later if write/marketplace scopes are ever needed — mixd has zero RFC 5849 code today.

    **Spec**:
    - `DiscogsAPIClient(BaseAPIClient)` with httpx2, Pydantic models; auth-strategy seam (token header now, OAuth 1.0a slot open)
    - Token storage + settings surface follow the Anthropic-key pattern: encrypted at rest via `oauth_tokens`, connect-gated UI
    - Rate model: Discogs throttles **by source IP** — every user of the instance (and anything sharing its egress) shares one 60/min counter (docs; [staff-confirmed](https://www.discogs.com/forum/thread/867991); probed 2026-08-20). Auth choice does not change throughput — OAuth 1.0a and personal tokens share the bucket
    - One instance-wide serialized fetch queue for Discogs API calls — a 5,000-item collection at `per_page=100` consumes ≈50 s of the whole instance's budget, so concurrent per-user fetches would starve each other
    - Header-authoritative throttling: pace ~40–45 req/min (starting point, revisit) and self-correct from `X-Discogs-Ratelimit-Remaining` — the counter can be non-zero on the first call
    - Unique `User-Agent` (`Mixd/<version> +<repo-url>`) — generic agents get silently lower limits
    - `i.discogs.com` image fetches bypass the API limiter (separate, undocumented bucket); ignore rate headers on image responses
    - Pagination stops at the 10,000-item ceiling; add a `discogs` `ConnectorAPIConfig` field to `APIConfig` (`src/config/settings.py`)
    - Key endpoints: `/users/{username}/collection/folders/0/releases` (full collection), `/releases/{id}` (release detail), `/masters/{id}` (master release)
    - Pydantic models for release, master, artist, label, format responses
    - Reuse: `_shared/http_client.py`, `_shared/retry_policies.py`

    **Tests**:
    - (unit) auth header injection + 401 → actionable reconnect error; (integration, mocked transport) pagination + rate-limit retry
    - (integration) two users' concurrent fetches serialize through one queue; a low `X-Discogs-Ratelimit-Remaining` slows the pacer; an image fetch consumes no API budget

    Effort: M | Dependencies: None | Status: Not Started

### v0.11.2: Spotify API Currency

**Goal**: The existing Spotify connection stays honest under Spotify's 2026 program changes — an expired grant says "reconnect", a quota exhaustion is not mistaken for a rate limit, and disconnect states exactly what it removes.

**Context**: The program facts this milestone responds to (effective dates, not predictions): refresh tokens expire 6 months after the original authorization, and a refresh does not extend the window ([policy, 2026-06-18](https://developer.spotify.com/blog/2026-06-18-refresh-token-expiration); enforced for existing apps 2026-07-20; expiry surfaces as HTTP 400 `invalid_grant`). API quota pools per developer account across all of the account's client IDs (2026-07-23); quota exhaustion returns a 429 whose body carries `reason: "QUOTA_EXCEEDED"` and does not clear on `Retry-After` timescales. Development-mode `GET /me` no longer returns `email`, `country`, or `product`; the `account_id` field (added 2026-05) is Spotify's designated key for external linkage. Endpoint reference: [provider-integration-research-2026-08.md](provider-integration-research-2026-08.md).

**What this unlocks**: a Spotify connector whose failure states are all actionable — and the shared re-auth substrate exercised on a live connector before v0.11.3 Tidal reuses it.

**Persona**: Curator-primary (their primary connector keeps working and says what it needs); Tinkerer secondary (CLI reconnect flow).

**Key Design Decisions**:
- **Expiry is handled where it surfaces** — the refresh POST is the one place `invalid_grant` appears, so detection, token deletion, and the `reauth_required` signal live in the auth layer; UI and CLI only render the state.

#### Spotify Currency Epics

- [ ] **Spotify Re-Auth & Reconnect**

    **Story**: The user whose grant aged out sees a "reconnect Spotify" prompt and is back in one click — instead of silent sync failures behind a swallowed warning.

    **Decisions**:
    - **Delete the dead token on `invalid_grant`** — a revoked refresh token can never succeed again; keeping it makes every later operation re-fail slowly.

    **Spec**:
    - Detect HTTP 400 `invalid_grant` on the refresh POST (`spotify/auth.py:196` — today `raise_for_status()` discards the body; `try_silent_refresh` (:361) swallows failures to a warning; `force_refresh` (:388) raises uncaught)
    - On detection: delete the stored token, raise `reauth_required` (v0.11.0 substrate); connector card + CLI status render the reconnect affordance
    - Persist `authorized_at` (Unix ts, `StoredToken.extra_data`) at grant time so grant age is knowable
    - Add the reconnect flow to `docs/web-ui/01-user-flows.md`; update `.claude/rules/spotify-api.md`

    **Tests**:
    - (unit) mocked 400 `invalid_grant` → token deleted, `reauth_required` raised; mocked 500 → retry path unchanged
    - (integration) the silent-refresh path surfaces `needs_reauth` instead of a swallowed warning

    Effort: M | Dependencies: Connector Auth-State Fidelity (v0.11.0) | Status: Not Started

- [ ] **Quota-429 Discrimination**

    **Story**: When the pooled account quota runs out, the user sees "Spotify quota exhausted" — not an endless rate-limit retry that cannot succeed.

    **Spec**:
    - `spotify/error_classifier.py`: split 429 handling on body `reason == "QUOTA_EXCEEDED"` vs plain rate-limit
    - Quota exhaustion skips the `Retry-After` backoff loop and emits a distinct log signal naming PDR-003 (pattern: the existing `_get_tracks_batch_impl` 403 instrumentation)

    **Tests**:
    - (unit) both 429 shapes classify differently; the quota body does not enter the rate-limit retry path

    Effort: S | Dependencies: None | Status: Not Started

- [ ] **Account Identity & Explicit Disconnect Semantics**

    **Story**: The user's Spotify link survives a display-name change, and disconnecting states exactly what it removes — credentials go, imported library and history stay theirs.

    **Decisions**:
    - **Disconnect removes credentials, not data** — imported likes, plays, and mappings are the user's records; account deletion (v0.6.4 purge) stays the full-removal path.

    **Spec**:
    - Adopt `account_id` from `GET /me` for external linkage; verify the live field name first (single-source claim)
    - Remove any read of `email`/`country`/`product` (absent in development mode)
    - Make disconnect explicit: `DELETE /api/v1/connectors/{service}/token` (`routes/connectors.py:129-147`) removes the token row and stops Spotify play polling; state the retained data on the disconnect confirm and in `docs/web-ui/01-user-flows.md`. (`spotify/personal_data.py` is the GDPR-export parser — unrelated to disconnect)

    **Tests**:
    - (unit) profile parse without `email`/`country`/`product` succeeds
    - (integration) disconnect deletes the token row and nothing else; status renders disconnected

### v0.11.3: Tidal Foundation

**Goal**: An authenticated Tidal client, conservative track resolution, and a favorites snapshot — the bones the v0.12.0 spike queries and v0.13.4 completes.

**Context**: Tidal's current API ([developer.tidal.com](https://developer.tidal.com/)) is JSON:API-shaped with first-class ISRC and barcode lookup, cursor pagination, and full playlist CRUD — the strongest catalog surface of the new connectors. It has no listening-history endpoint, so Tidal contributes library and playlist data, never plays. The legacy v1 API and the `tidalapi` PyPI library that drives it are deprecated; this connector builds only on the documented v2 API. Endpoint reference: [provider-integration-research-2026-08.md](provider-integration-research-2026-08.md).

**What this unlocks**: Tidal catalog access for the v0.12.0 spike (the sixth service); the client, auth, and resolution substrate v0.13.4 builds likes sync and playlist CRUD on.

**Persona**: Curator-primary (the Tidal library's on-ramp); Tinkerer secondary (an OAuth 2.1 + device-code auth model to inspect).

**Key Design Decisions**:
- **BYO client ID per deployment** — each deployment registers its own free app at developer.tidal.com (≤10 apps per account, ≤3 redirect URIs per app, app name ≤30 characters), so each instance holds its own throughput bucket and credentials. Matches the Spotify BYO-credentials posture.
- **OAuth 2.1 with PKCE S256, mandatory for every client** — `client_credentials` serves catalog-only calls.
- **Design rate handling to `Retry-After` only** — Tidal publishes no rate numbers; trust `expires_in` from the live token response rather than documented TTLs.
- **Vendor the OpenAPI spec, diff it in CI** — Tidal revises the API in place (the search contract changed 2026-08-12 and was fixed same-day, [#366](https://github.com/orgs/tidal-music/discussions/366)); a vendored `tidal-api-oas.json` plus a CI diff turns silent contract changes into visible failures. Generated client code stays in an isolated module wrapped by the adapter (import-linter enforced).

- [ ] **Tidal Auth & API Client**

    - `TidalErrorClassifier`; 429 honors `Retry-After`; add a `tidal` `ConnectorAPIConfig` field to `APIConfig` (`src/config/settings.py`)

    **Story**: Tidal tracks must connect to canonical tracks for the spike and later sync to mean anything — with the same discipline as Apple's v0.11.0 resolver: assert only what an identifier anchors.

    **Decisions**:

    **Spec**:
    - `TidalInwardResolver` + `TidalMatchingProvider`, ISRC path only: `GET /tracks?filter[isrc]=` (1:N, paginated; multi-ISRC batching returns one match per code — send one code per request)
    - Successor seam: a per-connector resolve-successor hook consulted for dead IDs; Tidal implements it via the `replacement` relationship; Spotify relinking and Apple equivalents migrate onto the seam
    - Reuse: `_shared/inward_track_resolver.py`, `_shared/matching_provider.py`, `_shared/isrc.py`

    **Tests**:
    - (unit) ISRC hit → `match_method="isrc"` mapping; no ISRC → observation stays unresolved, no `artist_title` mapping minted
    - (unit) a dead ID with a `replacement` pointer → typed succession recorded through the shared seam

- [ ] **Favorites Snapshot**
