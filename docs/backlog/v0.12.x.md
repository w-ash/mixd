# v0.12.x: First-Class Artists & Albums

For strategic overview, see the [planning overview](README.md).

## User Workflow Context

The user's music identity is bigger than their track list, but mixd models only tracks today. Artists are `{"names": ["..."]}` JSON strings — "Radiohead" on Spotify and "Radiohead" on Last.fm are unrelated text, so there is no artist page, no "all tracks by X", no favorites. Albums are a bare string column on tracks. This cycle promotes both to first-class entities on the same three-layer identity pattern as tracks — and it starts with a spike, because with the v0.11.x connector foundations in place, entity design can be measured against **six services' real catalog data** (Spotify, Last.fm, Apple Music, Discogs, Tidal, MusicBrainz) instead of assumed from two. The play-convergence work proved the method: investigate first, cite findings in every design decision.

Persona view (from the [alignment table](README.md#persona-alignment)): the **Weekly Curator** gets artist favorites and album browsing built on identity that holds up across services; the **Tinkerer** gets a rich relational model designed in the open (findings doc); the **Casual** listener gets the browse-by-artist/album navigation every music app is expected to have.

Cross-cutting contract (stated once — per-epic Specs reference it): every new use case this cycle must be classified in the chat-tool parity registry (`src/application/tools/registry.py`) — CI (`tests/unit/application/tools/test_registry_parity.py`) fails on any unclassified use case. Reads get a `ToolSpec` or an explicit classification; mutations additionally get two-phase confirmation wiring like the existing `*_write` dispatchers.

### v0.12.0: Entity Representation Spike

**Goal**: Before artists and albums get schemas, measure how every connected service actually represents them — with real catalog data, not assumptions.

**Context**: The play-convergence findings ([play-import-convergence-findings.md](play-import-convergence-findings.md)) turned guesses about timestamps and identity into measured facts that reshaped the design; this spike does the same for entity modeling. The v0.11.x clients make it possible: sample entities from the user's *existing* library and look the same artists/albums up in each service's **catalog** APIs — no personal Apple history or Discogs collection required. Docs-only milestone (precedent: v0.8.12).

**What this unlocks**: v0.12.1 and v0.12.2 Key Design Decisions that cite measurements instead of assumptions — alias handling sized against Discogs ANVs and MusicBrainz aliases, album modeling tested against real release-group/master divergence, multi-artist credit handling grounded in observed join-phrase chaos.

**Persona**: indirectly all three — this is the milestone that keeps the entity model from being redesigned after the third connector.

**Key Design Decisions**:
- **Catalog lookups, not personal history** — the sample comes from the user's existing `tracks` table; each service is queried for the *same* entities, so representations are directly comparable. Personal Apple/Discogs data is welcome when it exists but not required.
- **Findings doc is the deliverable and the gate** — v0.12.1 does not start until every census question has a recorded answer with a citing table (the play-findings pattern).

### v0.12.1: First-Class Artists

**Goal**: Promote artists from embedded JSON strings to first-class entities with identity resolution, favorites, web UI, and workflow integration.

**Context**: Artists are currently stored as `{"names": ["..."]}` JSON on Track and ConnectorTrack records — "Radiohead" on Spotify and "Radiohead" on Last.fm are unrelated text. This milestone gives artists their own identity, cross-service mapping, favorites, and dedicated pages, following the same three-layer pattern established for tracks.

**What this unlocks**: artist browsing and favorites in the web UI, "tracks by my favorite artists" workflows, and the artist-identity substrate that v0.12.2 albums and the v1.1.x social layer build on.

**Persona**: all three — the Curator favorites artists and builds artist-driven playlists; the Tinkerer explores the mapping model; the Casual listener finally gets browse-by-artist.

**Key Design Decisions**:
- **Favorites are Mixd-only** — users favorite artists in the UI, because the favorite is *their* curation signal, not a mirror of platform state. Service sync (e.g., Spotify followed artists) deferred to a future milestone.
- **`track_artists` join table** replaces JSON artist embedding on tracks — enables efficient "all tracks by artist X" queries and proper relational integrity.
- **Canonical artists are per-user, not global** — `tracks` is per-user today and cross-user identity is deliberately deferred to v1.1.0; a global artists table would smuggle in cross-user identity semantics (merge rights, shared edits) this cycle hasn't earned. `connector_artists` stays global like `connector_tracks` — service records are facts about the service, not the user.
- **Artist and album mappings are live rows; supersession stays a track capability** *(review 2026-09-15, [track-stack review](track-stack-review-2026-09-15.md))* — the five supersession columns on `track_mappings` exist because track ids die and relink; artist and album ids are treated as permanent. A generic mapping repository serves all three tables, so supersession can be switched on later as columns, not code.
- **Mappers are pure and resolution is an operation** — the track mapper's read-path promotion write is deleted in pre-flight rather than copied; MusicBrainz enrichment (1 req/s) runs as a resumable `OperationRun`, never on the import path, so an import mints artists from the ids it already holds and finishes in seconds.
- **Same-person projects are separate artists, linked — never merged** *(census 2026-09-14, [findings §2](entity-representation-findings.md))* — Caribou, Daphni and Manitoba are distinct ids on all six services; Discogs and MusicBrainz relate them (`aliases`, `is person`). A merge would make favorites and artist pages lie about which project the user listened to.
- **"Various Artists" is never an artist row** *([findings §4](entity-representation-findings.md))* — six unrelated sentinels exist and one (Discogs 194) is not even fetchable; it is an album-level flag (v0.12.2 `albums.is_various`). The backfill skips the sentinel *name*, keeping the track's credit row with a null artist, rather than minting a favoritable phantom.
- **The JSON→`track_artists` move is expand/contract, not a cutover** — the matching layer reads `artist_normalized`/`artists_text` precomputed from the JSONB today; a one-shot swap would put match confidence at risk mid-cycle. Expand (dual-write) → repoint readers → contract (drop the JSONB) as a separate final step, only after matching characterization tests pass against the new source.

#### Pre-Flight Refactors (hygiene — skimmers may skip)

Eight items scheduled for exactly this moment, because this cycle adds two more canonical ↔ mapping ↔ connector stacks and would otherwise copy the track stack's history along with its essentials. The 2026-09-15 review ([track-stack review](track-stack-review-2026-09-15.md), evidence with commit SHAs) found the copyable defects are not the supersession chain (≈540 lines, exercised in prod, kept) but ingest orchestration living in a repository (582 lines), a mapper that writes, five spellings of primary election, three sort registries, seven find-or-create sites with three gates, and 31 `match_method` literals. **Order matters**: (1) delete the healing write, (2) domain-typed match constants, (3) one keyset-sort declaration, then (3b) one page-fetch helper on the same seam — cheap and independent, first; (4) the defaults strip, with (5) likes as presence rows in the same fixture pass; (6) the resolve-and-record service, after the strip and before any artist ingest code exists; (7) the `db_models.py` split; (8) the generic mapping repository, after the split settles module homes.

Stack currency (checked 2026-09-15): SQLAlchemy 2.1 is at rc2 (2026-09-08) with the final release next and `pyproject.toml` carries no upper bound — pin `sqlalchemy<2.1` inside pre-flight 7 (2.1's `relationship.secondary` string-eval removal and unconditional autoflush are the two items to re-check at upgrade). PG18 is GA on Neon (2026-05-01) but this cycle stays on PG17; any generated column is written `STORED` explicitly so a later upgrade cannot flip it virtual, and ids stay `uuid.uuid7()` generated in Python. attrs 26 / PEP 649 need nothing; tuples on frozen entities remain the right shape.

Already in place (v0.8.6): `domain/repositories/interfaces.py` was split into per-aggregate modules (commit `96d56e42`) with no re-exporting `__init__` — this cycle's new repository protocols land in their own modules per that pattern. - [x] **Delete the read-path healing write**

- [ ] **One page-fetch helper** *(filed 2026-09-16 from the pre-flight 3 review)*

    **Story**: The user paging a library whose last page is exactly full gets a `next_cursor` that leads to an empty page, because the track listing decides "more pages" by `len(rows) == limit` while play events and operation runs probe `limit + 1`. - [ ] **Strip the `'default'` tenant fallback**

    **Story**: The user's rows must belong to the user who made them. Three phantom tenants were purged from production on 2026-09-06 ([record](v0.10.x.md#closed-residue-tenants-in-production-purged-2026-09-06)) — 17,723 rows that no account owned, and that nobody was ever told about, because a `user_id` nobody supplied was silently filled in. v0.10.4.1 closed the half of that door the session can see: a transaction *declaring* itself `DEFAULT_USER_ID` against a hosted database is refused. The other half is still open — a column default supplies the value without anyone declaring anything, so an INSERT that simply omits `user_id` still mints a tenant. Closing it makes that INSERT fail loudly instead, before this cycle adds ~10 more tenanted tables that would inherit the same fallback.

    **Decisions**:
    - **No fallback survives at any layer.** A default that is right in local dev and wrong in production is the whole defect; `DEFAULT_USER_ID` stays a local-dev convenience at the interface edge, never an entity field default or a column default.
    - **The 190 failures are the work, not a blocker.** Measured 2026-08-21: stripping both halves fails ~190 tests, and every dependency is a test fixture constructing rows without a tenant — not production code. Fixtures asserting a tenant explicitly is the point of the change, not collateral from it.
    - **Absorbs the v0.10.2.9 review's F8** (`Track.user_id` / `TrackLike.user_id` silent `'default'`), previously unscheduled: same footgun, same fixture migration, no reason to pay for it twice.

    **Spec**:
    - Migration: `ALTER COLUMN user_id DROP DEFAULT` across the affected tables — the docs say 23; confirm against the live schema (`information_schema.columns WHERE column_name = 'user_id' AND column_default IS NOT NULL`) rather than trusting the count
    - `default="default"` removed from the matching ORM columns in `src/infrastructure/persistence/database/db_models.py`
    - `user_id` required on every entity that defaults it today — nine fields in `src/domain/entities/`: `Track` and `TrackLike` (`track.py`), `Playlist` (`playlist.py`), `ResolutionEvent`, `ResolutionNegative`, `TrackMapping`, `MatchReview`, and `ConnectorTrackPlay` + `TrackPlay` (`operations.py`) — no default, so a construction site that forgets fails at the type checker
    - Fixture migration: `tests/fixtures` (`make_track` and friends) supply a tenant explicitly; prefer one shared default-tenant constant in the fixtures over ~190 literals
    - Optional, decide in flight: a repository write-path backstop rejecting a persist whose entity tenant disagrees with the ambient `user_context`

    **Tests**:
    - (integration) an INSERT omitting `user_id` raises `NotNullViolation` instead of creating a row
    - (integration) `alembic upgrade head` then `--autogenerate` yields an empty diff
    - (unit) `Track` / `TrackLike` cannot be constructed without a tenant

- [ ] **Generic mapping repository**

    **Story**: Tracks, artists and albums each need "assert a mapping, keep live rows unique, elect a primary, record the event" — one mechanism, three typed tables.

    **Decisions**:
    - **Three typed tables, not an `entity_kind` polymorphic table** — RLS is a per-table policy on `user_id`, FK semantics differ per entity (`RESTRICT` on `track_mappings.track_id` since migration 051), and the live-uniqueness partial index is per entity; a polymorphic key gains nothing on Neon PG17 and forfeits cascade.
    - **Supersession is a per-table capability** — the assert is ON CONFLICT touch-or-supersede where the table has the columns, plain touch where it does not; artist and album tables ship without them.
    - **Every entity kind records the same event fields** — `score`, `zone` and `selection_probability` are captured at queue time for artist and album decisions exactly as for tracks (memo §10.4); an entity whose review log lacks them can never be calibrated.
    - **Metadata drift is a touch, never a supersession** (memo §10.8.2) — a renamed Spotify artist updates `connector_artists.name` and moves the mapping's `last_seen_at`; nothing else changes, so the user's favorite survives every rename.

    **Spec**:
    - `MappingRepository[DBM, M]` generic over `(owner_id_col, connector_id_col)` providing assert, `live_only`, the manual-override filter, vacancy-fill election and `_record_assertion`; `TrackMappingRepository` becomes the track instantiation — the five public spellings of primary election collapse to one
    - `resolution_events` gains a nullable `entity_kind` (default `'track'`) — the table has no FKs by design, so artist and album decisions share it
    - Prevents ~700 lines × 2 entities

    **Tests**:
    - `test_mapping_supersession.py` (1,031 lines) passes against the generic instantiation; (integration) an artist mapping table round-trips assert/elect/event with no supersession columns

    Effort: M | Dependencies: Split `db_models.py` by Aggregate | Status: Not Started

#### Backend Data Model Epics

- [ ] **Artist Entity & Domain Model**

    **Story**: The user wants artists to *be something* in mixd — favoritable, mappable across services, filterable in workflows — so the domain needs an `Artist` with identity instead of a name string riding along on tracks.

    **Decisions**:
    - **The existing `Artist(name)` value object *is* the credit** — it is constructed at 16 source sites (11 files) and in 74 test files; renaming it `ArtistCredit` and adding the optional `artist_id` keeps `Track.artists` pure and makes the artist filter a plain transform over ids the entity already carries. The new `Artist` is the aggregate root; credits are value objects on Track and Album with no entity and no repository of their own.
    - **No `position` field on the credit** — the tuple's order *is* the position; a stored copy would be one more invariant to validate, and the row-builder enumerates when it writes `track_artists`.
    - **`ConnectorTrackRef.artists` stays `tuple[str, ...]`** (`entities/playlist.py`) — it is the display snapshot of an unresolved playlist entry, not a credit; it is deliberately not upgraded.
    - **A favorite is presence, not state** — `ArtistFavorite(artist_id, favorited_at)`, no `is_favorited`; favorites never sync to a service (see Key Design Decisions), so there is nothing for a tombstone to push.

### v0.12.2: First-Class Albums

**Goal**: Promote `album` from a string field on Track to a proper entity with identity resolution, cross-service mapping, and dedicated web UI.

**Context**: Albums are currently a bare `album` string column on the tracks table — "OK Computer" on Spotify and "OK Computer" on Last.fm are unrelated strings. This milestone gives albums their own identity, following the same three-layer pattern (canonical → mapping → connector) established for tracks and extended for artists in v0.12.1.

**What this unlocks**: album browsing with ordered track listings, and the album entity that physical media (v0.13.1) and manual listens (v0.13.2) require.

**Persona**: all three — album browsing is core navigation for everyone; the Curator additionally needs albums as the unit of physical ownership.

**Key Design Decisions**:
- **Album ≠ Release**: An "album" is the abstract work (MusicBrainz calls this a "release group"). A "release" is a specific pressing/edition (UK vinyl 1997, Japanese CD with bonus tracks). This milestone covers albums; v0.13.1 adds the release/pressing layer.
- **MusicBrainz release groups as canonical** — but release-group data is **not** in today's responses: `get_recording_by_isrc` requests `inc=artist-credits+releases` and `MusicBrainzRelease` models only `id`+`title`. This milestone extends the lookup to `inc=release-groups` and widens the model — same call, richer `inc`, 1 req/s budget unchanged.
- **Album membership and ordering are edition facts on `connector_tracks`, not a tenanted `album_tracks`** *(review 2026-09-15)* — track numbers differ per edition (OK Computer is 12 tracks on Spotify, 16 on the Discogs main release — [findings §7](entity-representation-findings.md)) and Spotify's album id already sits on every connector track. The canonical listing is "tracks whose primary mapping's connector track sits on an edition mapped to this album", ordered by that edition; v0.13.1 pressing-level ordering comes free. A track with no connector row (v0.13.2 manual listens) has no album until it is matched — accepted.
- **Album artists vs track artists**: An album has its own artist(s). `album_artists` join table parallels `track_artists` from v0.12.1, with `albums.is_various` instead of a "Various Artists" row — six services, six unrelated sentinels, and DJ mixes are credited to the DJ on four of them ([findings §4](entity-representation-findings.md)).
- **The edition string lives on the mapping, not the album** *(census 2026-09-14, [findings §5](entity-representation-findings.md))* — 15/33 sampled library album titles are Spotify edition names ("(Expanded Edition)", "(Remastered)") that Discogs and MusicBrainz never use as the work's title; OKNOTOK has no work-level entity anywhere. Dedup and match on the qualifier-stripped title; the service's edition id and title stay on `connector_albums`.
- **Cover art stays in `connector_albums.raw_metadata`** *(review 2026-09-15)*, read through a mapper accessor — the v1.1.x/v1.2.x share cards fetch one album at a time, so a column waits until a query needs one (the `artist_relations` precedent).
- **External identifiers are references, never keys** — `release_group_mbid` and `barcode` are indexed and non-unique, per the v0.12.1 schema decision.

- [ ] **Album Identity Resolution**

    **Story**: One album page per album — "OK Computer" from Spotify and Last.fm resolve to the same canonical entity with unified detail.

    **Decisions**:
    - **Import mints, an operation enriches** — same split as artists: the import path creates albums from the Spotify album ids already on connector tracks through the resolve-and-record service; MusicBrainz release-group lookups run as a resumable `OperationRun`.
    - Confidence scoring mirrors track/artist matching — the same `MatchEvaluationService` zones, and a concrete `AlbumEvidence` attrs class over `connector_id | barcode | release_group | stripped_title` (the third evidence type — the moment an `Evidence` protocol earns its place, if the three still share a shape).

    **Spec**:
    - Cross-service album matching (Spotify album ID ↔ Last.fm album ↔ MusicBrainz release group), with **barcode as the strongest edition-level key** — a `connector_albums.barcode` hit across services is an id match; MB release-group `url-rels` link 26/30 sampled groups to their Discogs master ([findings §8](entity-representation-findings.md))
    - MusicBrainz: extend `get_recording_by_isrc` to `inc=release-groups` and widen `MusicBrainzRelease` (today `id`+`title` only) with release-group id, primary/secondary types, first-release-date, and the release's `barcode`; an edition track (OKNOTOK disc 2) resolves to the OK Computer release group by construction
