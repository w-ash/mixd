# v0.12.x: First-Class Artists & Albums

For strategic overview, see the [planning overview](README.md).

## User Workflow Context

The user's music identity is bigger than their track list, but mixd models only tracks today. Artists are `{"names": ["..."]}` JSON strings — "Radiohead" on Spotify and "Radiohead" on Last.fm are unrelated text, so there is no artist page, no "all tracks by X", no favorites. Albums are a bare string column on tracks. This cycle promotes both to first-class entities on the same three-layer identity pattern as tracks — and it starts with a spike, because with the v0.11.x connector foundations in place, entity design can be measured against **six services' real catalog data** (Spotify, Last.fm, Apple Music, Discogs, Tidal, MusicBrainz) instead of assumed from two. The play-convergence work proved the method: investigate first, cite findings in every design decision.

Persona view (from the [alignment table](README.md#persona-alignment)): the **Weekly Curator** gets artist favorites and album browsing built on identity that holds up across services; the **Tinkerer** gets a rich relational model designed in the open (findings doc); the **Casual** listener gets the browse-by-artist/album navigation every music app is expected to have.

Cross-cutting contract (stated once — per-epic Specs reference it): every new use case this cycle must be classified in the chat-tool parity registry (`src/application/tools/registry.py`) — CI (`tests/unit/application/tools/test_registry_parity.py`) fails on any unclassified use case. Reads get a `ToolSpec` or an explicit classification; mutations additionally get two-phase confirmation wiring like the existing `*_write` dispatchers.

### v0.12.0: Entity Representation Spike

**Goal**: Before artists and albums get schemas, measure how every connected service actually represents them — with real catalog data, not assumptions.

**Context**: The play-convergence findings ([play-import-convergence-findings.md](play-import-convergence-findings.md)) turned guesses about timestamps and identity into measured facts that reshaped the design; this spike does the same for entity modeling. The v0.11.x clients make it possible: sample entities from the user's *existing* library and look the same artists/albums up in each service's **catalog** APIs — no personal Apple history or Discogs collection required. Docs-only milestone (precedent: v0.8.12).

**What this unlocks**: v0.12.1 and v0.12.2 Key Design Decisions that cite measurements instead of assumptions — alias handling sized against Discogs ANVs and MusicBrainz aliases, album modeling tested against real release-group/master divergence, multi-artist credit handling grounded in observed join-phrase chaos.

**Persona**: indirectly all three — this is the milestone that keeps the entity model from being redesigned after the third connector.

**Key Design Decisions**:
- **Catalog lookups, not personal history** — the sample comes from the user's existing `tracks` table; each service is queried for the *same* entities, so representations are directly comparable. Personal Apple/Discogs data is welcome when it exists but not required.
- **Findings doc is the deliverable and the gate** — v0.12.1 does not start until every census question has a recorded answer with a citing table (the play-findings pattern).

#### Pre-Flight Refactors (hygiene — skimmers may skip)

The track-stack hygiene the artist and album stacks are specified on top of, shipped as revisions of this spike so the v0.12.1 row means artists: **v0.12.0.1** carries tranche 1 (items 1–3 and the constraint/repair follow-up, shipped 2026-09-17); **v0.12.0.2** carries tranche 2 (3b and 4–8).

Already in place (v0.8.6): `domain/repositories/interfaces.py` was split into per-aggregate modules (commit `96d56e42`) with no re-exporting `__init__` — this cycle's new repository protocols land in their own modules per that pattern. - [x] **Strip the `'default'` tenant fallback**

    **Story**: The user's rows must belong to the user who made them. Closing it makes that INSERT fail loudly instead, before this cycle adds ~10 more tenanted tables that would inherit the same fallback.

- [x] **Generic mapping repository**

    **Story**: Tracks, artists and albums each need "assert a mapping, keep live rows unique, elect a primary, record the event" — one mechanism, three typed tables.

    **Decisions**:
    - **Three typed tables, not an `entity_kind` polymorphic table** — RLS is a per-table policy on `user_id`, FK semantics differ per entity (`RESTRICT` on `track_mappings.track_id` since migration 051), and the live-uniqueness partial index is per entity; a polymorphic key gains nothing on Neon PG17 and forfeits cascade.
    - **Supersession is a per-table capability** — the assert is ON CONFLICT touch-or-supersede where the table has the columns, plain touch where it does not; artist and album tables ship without them.
    - **Every entity kind records the same event fields** — `score`, `zone` and `selection_probability` are captured at queue time for artist and album decisions exactly as for tracks (memo §10.4); an entity whose review log lacks them can never be calibrated.
    - **Metadata drift is a touch, never a supersession** (memo §10.8.2) — a renamed Spotify artist updates `connector_artists.name` and moves the mapping's `last_seen_at`; nothing else changes, so the user's favorite survives every rename.

    **Spec**:
    - `MappingRepository[DBM, M]` generic over `(owner_id_col, connector_id_col)` providing assert, `live_only`, the manual-override filter, vacancy-fill election and `_record_assertion`; `TrackMappingRepository` becomes the track instantiation — the five public spellings of primary election collapse to one
    - `resolution_events` gains `entity_kind` (`NOT NULL`, CHECK over `track|artist|album`, backfilled `'track'`) — the table has no FKs by design, so artist and album decisions share it
    - Prevents ~700 lines × 2 entities

### v0.12.1: First-Class Artists

**Goal**: Promote artists from embedded JSON strings to first-class entities with identity resolution, favorites, web UI, and workflow integration.

**Context**: Artists are currently stored as `{"names": ["..."]}` JSON on Track and ConnectorTrack records — "Radiohead" on Spotify and "Radiohead" on Last.fm are unrelated text. This milestone gives artists their own identity, cross-service mapping, favorites, and dedicated pages, following the same three-layer pattern established for tracks.

**What this unlocks**: artist browsing and favorites in the web UI, "tracks by my favorite artists" workflows, and the artist-identity substrate that v0.12.2 albums and the v1.1.x social layer build on.

**Persona**: all three — the Curator favorites artists and builds artist-driven playlists; the Tinkerer explores the mapping model; the Casual listener finally gets browse-by-artist.

**Key Design Decisions**:
- **Favorites are Mixd-only** — users favorite artists in the UI, because the favorite is *their* curation signal, not a mirror of platform state. Service sync (e.g., Spotify followed artists) deferred to a future milestone.
- **`track_artists` join table** replaces JSON artist embedding on tracks — enables efficient "all tracks by artist X" queries and proper relational integrity.
- **Canonical artists are per-user, not global** — `tracks` is per-user today and cross-user identity is deliberately deferred to v1.1.0; a global artists table would smuggle in cross-user identity semantics (merge rights, shared edits) this cycle hasn't earned. `connector_artists` stays global like `connector_tracks` — service records are facts about the service, not the user.
- **Artist and album mappings are live rows; supersession stays a track capability** *(review 2026-09-15, [track-stack review](track-stack-review-2026-09-15.md))* — the five supersession columns on `track_mappings` exist because track ids die and relink; artist and album ids are treated as permanent. A generic mapping repository serves all three tables, so supersession can be switched on later as columns, not code.
- **Mappers are pure and resolution is an operation** — the track mapper's read-path promotion write is deleted in pre-flight rather than copied; MusicBrainz enrichment (1 req/s) runs as a resumable `OperationRun`, never on the import path, so an import mints artists from the ids it already holds and finishes in seconds.
- **Same-person projects are separate artists, linked — never merged** *(census 2026-09-14, [findings §2](entity-representation-findings.md))* — Caribou, Daphni and Manitoba are distinct ids on all six services; Discogs and MusicBrainz relate them (`aliases`, `is person`). A merge would make favorites and artist pages lie about which project the user listened to.
- **"Various Artists" is never an artist row** *([findings §4](entity-representation-findings.md))* — six unrelated sentinels exist and one (Discogs 194) is not even fetchable; it is an album-level flag (v0.12.2 `albums.is_various`). The backfill skips the sentinel *name*, keeping the track's credit row with a null artist, rather than minting a favoritable phantom.
- **The JSON→`track_artists` move is expand/contract, not a cutover** — the matching layer reads `artist_normalized`/`artists_text` precomputed from the JSONB today; a one-shot swap would put match confidence at risk mid-cycle. Expand (dual-write) → repoint readers → contract (drop the JSONB) as a separate final step, only after matching characterization tests pass against the new source.

### v0.12.2: First-Class Albums

**Goal**: Promote `album` from a string field on Track to a proper entity with identity resolution, cross-service mapping, and dedicated web UI — as the third instantiation of the entity stack, not a third copy of it.

**Context**: Albums are currently a bare `album` string column on the tracks table — "OK Computer" on Spotify and "OK Computer" on Last.fm are unrelated strings. v0.12.1 built the artist stack on the track stack's pattern and, in doing so, showed exactly which parts are entity-generic and which were written artist-shaped by accident: the minting walk existed twice until a review caught it, the enrichment operation hand-rolled its own owner probe, and the evidence scoring, connector-record repository and credit-row writer are all artist-named copies of what albums need. This milestone first lifts those mechanisms into generic form (pre-flight, shipped as v0.12.1 revisions), then adds albums as recipes and instantiations.

**What this unlocks**: album browsing with ordered track listings, the album entity that physical media (v0.13.1) and manual listens (v0.13.2) require, and an entity stack where the fourth entity (a label, a release) is a recipe, not a milestone.

**Persona**: all three — album browsing is core navigation for everyone; the Curator additionally needs albums as the unit of physical ownership; the Tinkerer gets an entity model with one mechanism per concern.

**Key Design Decisions**:
- **Third entity generalizes, never clones** *(v0.12.1 retrospective, 2026-09-21)* — every mechanism an album needs already exists for artists: the minting walk (`ArtistMinter`), the enrichment run (`EnrichArtistsUseCase`), levelled evidence (`calculate_artist_confidence`), the connector-record repository, the credit-row writer. Each is lifted to a generic mechanism plus an artist recipe in pre-flight, before any album code exists, so the album epics below are recipes and instantiations. A mechanism that would need an `if entity == "album"` branch is the wrong seam.
- **Two canonicals on one external id is a mapping-layer state, not just a column note** — v0.12.1's review found the MusicBrainz mapping asserted unconditionally while `artists.mbid` was documented as "a reference, never a key"; two artists on one MBID hijacked each other's mapping. Albums meet this case routinely (edition splits, release-group merges), so the rule lives in the generic mapping repository: on a non-superseding table the first claimant keeps the mapping, a later claimant is reported, never re-pointed.
- **Shared connector tables have exactly one authoritative writer per column** — `connector_artists` rows were clobbered by enrichment writing one user's canonical name over the service's own spelling. `connector_albums` is global with two writers (import, enrichment) and its barcode comes only from enrichment: the import owns the service's title and payload, enrichment may only add `barcode`/`family_identifier` and touch freshness (`ensure_*`, never the full upsert).
- **Album ≠ Release**: An "album" is the abstract work (MusicBrainz "release group"). A "release" is a specific pressing/edition. This milestone covers albums; v0.13.1 adds the release/pressing layer.
- **MusicBrainz release groups as canonical** — release-group data is **not** in today's responses: `get_recording_by_isrc` requests `inc=artist-credits+releases` and `MusicBrainzRelease` models only `id`+`title`. This milestone extends the lookup to `inc=release-groups` and widens the model. Search returns no relations and lookups do (measured on artists: the first enrichment pass seeded nothing until a lookup followed the search), so the budget is two MusicBrainz calls per newly identified album at 1 req/s.
- **Album membership and ordering are edition facts on `connector_tracks`, not a tenanted `album_tracks`** *(review 2026-09-15)* — track numbers differ per edition (OK Computer is 12 tracks on Spotify, 16 on the Discogs main release — [findings §7](entity-representation-findings.md)) and Spotify's album id already sits on every connector track. The canonical listing is "tracks whose primary mapping's connector track sits on an edition mapped to this album", ordered by that edition; v0.13.1 pressing-level ordering comes free. A track with no connector row (v0.13.2 manual listens) has no album until it is matched — accepted.
- **Album artists vs track artists**: An album has its own artist(s). `album_artists` parallels `track_artists` through the same credit-row writer, with `albums.is_various` instead of a "Various Artists" row — six services, six unrelated sentinels, and DJ mixes are credited to the DJ on four of them ([findings §4](entity-representation-findings.md)).
- **The edition string lives on the mapping, not the album** *(census 2026-09-14, [findings §5](entity-representation-findings.md))* — 15/33 sampled library album titles are Spotify edition names that Discogs and MusicBrainz never use as the work's title; OKNOTOK has no work-level entity anywhere. Dedup and match on the qualifier-stripped title; the service's edition id and title stay on `connector_albums`.
- **A name search identifies only on exact agreement** *(v0.12.1 measured: 29 of 137 local artists are genuine collisions and correctly stay pending)* — for albums the agreeing spelling is the qualifier-stripped title **and** the primary artist credit, both normalized; a tie between candidates leaves the album unidentified and reported, never guessed.
- **Cover art stays in `connector_albums.raw_metadata`** *(review 2026-09-15)*, read through a mapper accessor — the v1.1.x/v1.2.x share cards fetch one album at a time, so a column waits until a query needs one (the `artist_relations` precedent).
- **External identifiers are references, never keys** — `release_group_mbid` and `barcode` are indexed and non-unique, per the v0.12.1 schema decision.

Already in place (v0.12.1): revalidate-by-default HTTP cache policy (new album routes need no `_CACHE_POLICIES` entry); `KeysetSort.computed` for side-map sorts; `uow.get_artist_minter()` as the sanctioned domain-protocol-plus-accessor seam; `query_library(entity=…)` as the chat read surface; `artist_url` as a `ConnectorConfig` hook read through `external_urls`; web primitives `useKeysetPagination`, `SortableHead`, `DetailField`/`DetailSection`, `MappingBadges`, `TrackTable`; Apple artist ids confirmed equal to the trailing url-rel segment (findings §1a).

Before Wave 1: re-verify every identifier the Specs below name against the code (v0.12.1's spec named a renamed method, a wrong node-id prefix and stale site counts), and re-verify Tidal `replacement`/`version`/`numberOfVolumes` live (findings §9.8 — still open; it matters more for albums than it did for artists). Live verification on the local stack against flows 8.3/8.4 is a mandatory step before ship: on artists it found three defects the suites passed over.

#### Pre-Flight Refactors (hygiene — skimmers may skip)

Shipped as revisions of v0.12.1 (`v0.12.1.N`) before the album epics start, in this order: the claim policy first (both later mechanisms rely on it), then the connector-record repository, then the minter and the enrichment run (which consume both), then evidence and credit rows (independent). Each item deletes the artist-specific code it generalizes in the same change — no parallel copies survive a pre-flight.

- [ ] **Mapping claim policy**

    **Story**: The user whose library holds two canonical artists (or albums) on one MusicBrainz id must not watch the mapping flip between them on every enrichment run. v0.12.1 fixed this for the MusicBrainz artist mapping with a hand-rolled owner probe in the use case; the url-rel path has a second copy, and albums would need a third.

    **Decisions**:
    - **The rule lives in the mechanism** — on a table without supersession, `assert_mappings` holds the first claimant and reports later ones, because that is a fact about the live-uniqueness key, not about artists.

    **Spec**:
    - `MappingRepository.assert_mappings` on a `MappingShape(supersession=False)` returns the rows it refused in `MappingAssertion.held: Mapping[UUID, UUID]` (connector row → holding owner) instead of rewriting in place; same-owner re-asserts are a `touch`. Superseding tables keep today's semantics

    - `ArtistMinter` keeps the planner's strong-owner probe (that is identity resolution, not claim policy) but no longer needs `batch.claimed`

    **Tests**:
    - (integration) generic mapping suite: second claimant on a non-superseding shape is held and reported, first keeps primacy; superseding shape unchanged

- [ ] **Entity-generic minter**

- [ ] **Entity-generic enrichment run**
