# v0.10.x: Play History & Mapping Integrity

For strategic overview, see the [planning overview](README.md).

## User Workflow Context

The user's listening happens across services that disagree about everything — track identity, timestamps, detail — and mixd's merge of them depends on arrival order: measured against real data, one import order double-counts 58% of overlapping plays that the opposite order merges correctly ([findings](play-import-convergence-findings.md)). Meanwhile the mapping layer that underpins every import overwrites its own history in place — flip-flops are invisible, and rejected match candidates leave no memory, so the same wrong candidate is re-fetched and re-rejected forever.

This cycle fixes the data layer before anything else is built on it, while the window is open: production holds **zero** play rows today, so the defects can be fixed *before* the first at-scale import instead of repaired after it — no collapse scripts or rebuilds ever touching prod data. v0.10.0 makes canonical plays a deterministic projection of an immutable observation ledger (order-free, re-import-safe, richest-field-wins); v0.10.1 adds continuous polling of Spotify's recently-played API — live play counts for workflows within the hour, with GDPR uploads later deepening the same plays instead of duplicating them; v0.10.2 makes identity mappings append-only (supersession + resolution event log) so the v0.11.x connectors mint mappings with succession semantics from birth instead of forcing a migration. The first at-scale import (full Last.fm history + a fresh GDPR export) is v0.10.0/v0.10.1's joint acceptance, and every later cycle ships into an already-honest history.

Persona view (from the [alignment table](README.md#persona-alignment)): the **Weekly Curator** finally gets play counts they can trust and history that stays current unattended; the **Tinkerer** gets the observation ledger, rebuild command, and audit-grade mapping history to script against; the **Casual** listener gets history that "just works" no matter what they connect or re-import.

Cross-cutting contract (stated once — per-epic Specs reference it): every new use case this cycle must be classified in the chat-tool parity registry (`src/application/tools/registry.py`) — CI (`tests/unit/application/tools/test_registry_parity.py`) fails on any unclassified use case. Reads get a `ToolSpec` or an explicit classification; mutations additionally get two-phase confirmation wiring like the existing `*_write` dispatchers.

### v0.10.0: Convergent Play History

**Goal**: Make canonical play history a deterministic projection of imported source data — re-importing changes nothing, import order changes nothing, and each play carries the richest field values any source has offered.

**Context**: The sources report the same listening event differently — Spotify's export stamps the *end* of a play with `ms_played` and behavioral detail; Last.fm stamps the *start* with second precision and name-guessed track identity; manual listens are authored. Cross-source dedup (v0.4.10) merges them, but the outcome depends on arrival order: measured against real overlap data, Spotify-first merged 519 pairs correctly while Last.fm-first double-counted 267 (58% of that window's Last.fm plays) — same data, opposite orders, opposite results. All evidence, tolerances, and per-field trust rates are quantified in the [convergence findings](play-import-convergence-findings.md); this section's decisions cite it by section.

**What this unlocks**: trustworthy play counts and history-derived features (metrics, "loved but forgotten", the v0.13.2 physical-listen story) that stop drifting as sources are added or re-imported; a rebuild command that re-derives history from source records at any time; the substrate any future source (v0.10.1 polling, Apple Music, ListenBrainz) joins with zero new dedup code. Critically, per Findings §1 **no environment holds play data at scale yet** — the first big import is the real migration, which is why this milestone opens the cycle.

**Persona**: Curator-primary — their history *is* the product, and "own my listening data" only means something if the data is honest. Tinkerer secondary (rebuild/inspect commands, ledger to explore).

**Key Design Decisions**:
- **Canonical plays are a projection of the `connector_plays` observation ledger, not mutated-in-place records** — every source record is an immutable, bitemporal observation (event time + ingestion time); canonical state is a pure function of the observation *set*. This makes the merge associative, commutative, and idempotent by construction (a join-semilattice), which is what guarantees re-imports, arrival order, and batch boundaries can't change the result. In-place merging cannot be retrofitted to order-independence: re-merging on a richer late arrival needs the original per-source values, which only the ledger retains.
- **Grouping keys on observation channels — `(service, import_source)` — not services** — `spotify/spotify_export` and `spotify/spotify_api` are two observers of the same listen (v0.10.1), exactly like `lastfm` and `mixd` are; one grouping rule covers cross-service dedup, export↔API dedup, and the scrobble round-trip, so new channels need no new code.
- **Per-field survivorship, channel priority `spotify_export > spotify_api > mixd > lastfm`** — richest data wins per *attribute*, not per record (MDM golden-record practice): `ms_played` from export, timestamps from the highest-precision member, `loved` from Last.fm. `mixd` outranks `lastfm` so a round-tripped scrobble enriches the manual listen it echoes rather than displacing it.
- **`played_at` is stored as normalized start time** — Findings §3 validates the model (end − `ms_played` aligns sources to ±5s for 80% of true pairs; unnormalized, 92% would miss); converging at write kills the per-winner timestamp drift.
- **Tolerances: 30s tight, 180s fallback, greedy nearest one-to-one** — Findings §3/§4: 30s catches 82.7% of true pairs, the 30–180s band is real (pause-skewed, negative-heavy), ambiguity within windows is rare — nearest-first one-to-one assignment keeps skip-restarts distinct without probabilistic machinery.
- **Divergence bridging is exact-normalized only; the cure is upstream** — Findings §5b: all observed divergence (191 pairs) is casing/punctuation ("striptease" vs "Striptease") from Last.fm-created canonicals; an exact `normalize_for_comparison` bridge catches it at the play layer, and the casing fix epic removes the source. Fellegi–Sunter escalation explicitly not needed (§8.3).
- **Same-channel collapse for identical `(ts, identifier)` with differing `ms_played`** — Findings §7: 266 such pairs exist inside the GDPR export itself and would defeat the ON CONFLICT key; they are one observation (keep max `ms_played`).
- **Harden constraints before the first at-scale import** — Findings §5c: the NULL-`ms_played` hole in both dedup constraints has simply never been triggered; with no precious data anywhere (§1), fixing schema now is free.

#### Foundation Epics

- [x] **Ledger Idempotency Hardening**

    **Story**: The user re-runs an import — or uploads the same GDPR file twice — and nothing changes. Today a `mode=full` Last.fm re-import would duplicate every scrobble: Last.fm rows always have `ms_played = NULL`, both dedup constraints include `ms_played`, and NULL ≠ NULL means ON CONFLICT never fires ([Findings §5c](play-import-convergence-findings.md)).

    **Decisions**:
    - **`NULLS NOT DISTINCT` over a sentinel value** (e.g. `ms_played = -1`) — a sentinel leaks into every consumer that averages or sums listening time; the constraint option confines the fix to the schema.
    - **Defensive duplicate-collapse pre-pass ships in the migration even though all environments are currently clean** (Findings §1/§5c) — migrations must be correct wherever they run, including a database that re-imported before upgrading.

    **Spec**:
    - Migration: recreate `uq_track_plays_deduplication` and `uq_connector_plays_deduplication` with `NULLS NOT DISTINCT` (PG15+; prod is PG17)
    - Pre-pass (batched, outside the DDL transaction): collapse exact-duplicate groups keeping lowest `id`
    - `db_models.py`: constraint args updated to match

    **Tests**:
    - (integration) NULL-`ms_played` exact re-insert now conflicts on both tables; collapse pre-pass idempotent
    - (manual) `mixd` Last.fm full import twice → identical row counts

    Effort: M | Dependencies: None | Status: Completed (2026-07-17) — migration `040_plays_nulls_not_distinct` (id shortened: `alembic_version.version_num` is VARCHAR(32)); batched pre-pass via the repo's first `autocommit_block` with the 035 RLS bracket; en route, `bulk_insert_ignore_conflicts` counts were found unreliable (psycopg3 reports rowcount −1 for compiled inserts) and now count via `RETURNING id`

Partial index = migration `041_unresolved_partial_index`. #### Projection Epics

- [x] **Deterministic Merge & Grouping Domain Module**

    **Story**: One pure function decides what a canonical play is, so the answer never depends on which import ran first — today opposite arrival orders produce 519 correct merges vs 267 double-counts on the same overlap data (Findings §5a).

    **Decisions**:
    - **The module is channel-generic from day one** — v0.10.1's `spotify_api` and Apple Music channels must join with zero new dedup code; that claim is v0.10.1's acceptance test.
    - **Property tests are the ACI laws** — permutation invariance, idempotence, and batch-boundary invariance are the convergence guarantee stated as executable properties; a merge that passes them cannot be order-dependent.

    **Spec**:
    - New `src/domain/matching/play_projection.py`, evolving `play_dedup.py` (keep `_normalize_to_start_time`, `_get_tolerance`, tolerance constants). Per-channel behavior consolidates into one frozen `ChannelSpec` registry — channel → priority rank, time semantics (start/end), tolerance override — replacing service-keyed `END_TIME_SERVICES` and the loose priority tuple; priority order `("spotify_export", "spotify_api", "mixd", "lastfm")`. A future channel (Apple, ListenBrainz) is one registry entry — this registry *is* the multi-service seam
    - `group_ledger_entries(entries) -> list[PlayGroup]`: bucket by `resolved_track_id`; bridge buckets on exact `normalize_for_comparison(artist)::title` equality within tolerance (bridged groups emit a `resolution_divergence` stat); same-channel collapse for identical `(played_at, identifier)` differing `ms_played` (keep max); greedy nearest one-to-one cross-channel assignment (sort by |Δstart|, then channel priority, then `id`) + union-find
    - `merge_group(group) -> CanonicalPlayFields` survivorship: `played_at` = normalized start of highest-precision member; `ms_played` = first non-null by priority; `context` = winner flat + `merged_from_<channel>` sub-objects (preserves today's persisted shape); `source_services` = priority-sorted union of services; ties broken by lowest `id` (uuid7, time-ordered)
    - Domain-pure: entries passed in, nothing fetched; constants are module-level `Final` per domain rules

    **Tests**:
    - (unit, hypothesis) permutation invariance: any partition of entries into batches, any order → identical groups and fields; idempotence: re-projecting projected input is a no-op; two skips 20s apart never merge; bridge unions only exact-normalized keys

    Effort: L | Dependencies: None | Status: Completed (2026-07-17) — `play_projection.py` shipped with the repo's first hypothesis property tests. Union-find carries per-component channel sets: two components union only when their channel sets are disjoint (≤1 observation per channel per event), which keeps skip-restarts distinct even through cross-channel chains. `timestamp_quality` added to `ChannelSpec` (lastfm's native start outranks the export's pause-skewed derived start, per Findings §3). Context builders ported to domain byte-identically — required because the rebuild has no resolver in the loop — with a characterization test pinning domain ↔ resolver parity

- [x] **Projection Pipeline in the Import Path**

    **Story**: The user imports Last.fm then uploads GDPR files — or the reverse, or both twice — and gets byte-identical canonical plays. This is the property the user can personally verify, and the milestone's manual acceptance test.

    **Decisions**:
    - **`track_plays` keeps its exact shape** — only writers change; every reader (aggregations, recent plays, metrics, workflows) is untouched.
    - **Membership is materialized in a `play_sources` join table** — idempotence becomes a mechanical no-op diff (unchanged group → no writes), and provenance survives without parsing `context`.
    - **`play_dedup.py` and `bulk_update_play_source_services` are deleted after cutover** — clean break; two merge paths would reintroduce the disagreement this milestone removes.

### v0.10.1: Continuous Play Polling

**Goal**: Play history flows in continuously — Spotify's recently-played API is polled on the existing scheduler before plays age out of its ~50-play window, with Apple Music joining as the next channel in v0.11.0 — and the workflow surfaces that consume it stop lying about their own state: a save is visible the moment it lands, and a run is visible wherever the user is watching, whatever started it.

**Context**: The GDPR export delivers depth but arrives weeks late and ends the day it was requested (the user's current export stops 2025-02-28 — everything since exists only in Last.fm). Last.fm is live but identity-weak. Polling the source APIs adds a fresh, strong-identity observer: play counts land within the hour, and the convergence projection (v0.10.0) guarantees the later GDPR upload deepens those same plays (`ms_played`, skip/shuffle behavior) instead of duplicating them. This is the always-on-ingestion component [PDR-001](../decisions/PDR-001-data-ownership-model.md) identified as structural: missed polls are permanent data loss.

**What this unlocks**: live play-count workflows — "filter out tracks I already listened to today", "skip this week's heavy rotation" — plus redundancy where Last.fm misses and coverage after the export window closes.

**Persona**: Curator-primary (their workflows finally see today's listening); Tinkerer secondary (schedule + checkpoint surfaces to script against).

**Key Design Decisions**:
- **Polling rides the existing scheduler and sync-dispatch infrastructure** — `run_scheduler_loop` (v0.8.2) already dispatches per-user sync targets under their RLS + OAuth identity; a poller is a `SYNC_DISPATCH` entry, not new infrastructure. The `("spotify", "plays")` checkpoint combination is already declared in `CHECKPOINT_COMBINATIONS`, never produced.
- **Freshness is demand-pulled; the timer only guarantees coverage** — play counts must be current at the moments they're *consumed* (the user in the app, an agent reading over MCP, a workflow about to run), and those are all hookable events. The background heartbeat exists solely so plays don't age out of the ~50-play API window between sessions, and it adapts to the user's actual listening rhythm instead of firing hourly into silence.
- **API plays are a new observation channel (`spotify_api`), same service** — no `ms_played`, but per-play `played_at` and strong URI identity; the v0.10.0 channel-keyed grouping merges them with export and Last.fm observations with zero new dedup code (this is that module's acceptance claim, tested here).
- **Spotify API `played_at` start-vs-end semantics are calibrated, not assumed** — the export's end-time semantics were only confirmed empirically (Findings §3); the first real poll is compared against overlapping Last.fm scrobbles before its tight tolerance is trusted.
- **Apple Music is the next channel, not this milestone's** — its play channel (no timestamps → poll-window-approximated `played_at`, presence-only precedence) ships with the connector bones in [v0.11.0](v0.11.x.md#v0110-apple-music-foundation); the channel-generic grouping here is what makes that a zero-dedup-code addition.

- [x] **Spotify Recently-Played Importer**

    **Story**: The user wants today's listening to count today — a workflow filtering on "played this week" should see this morning's plays, not wait weeks for a GDPR export that ends the day it was requested. This importer is the missing live observer: strong-identity plays land within the polling interval, Last.fm covers the gaps, and the eventual export deepens these same plays (`ms_played`, skip behavior) instead of duplicating them.

    **Decisions**:
    - **No new resolver — reuse is the point, and the proof** — API rows carry `spotify:track:` URIs, so they resolve through the existing `SpotifyConnectorPlayResolver` unchanged (orchestrator Phase 2 already groups by `connector_name`), and their `ChannelSpec` is already registered: this milestone adds an importer and nothing else. That *is* v0.10.0's zero-new-dedup-code acceptance claim being cashed; a third resolver would restart the copy-paste drift the v0.10.0 review just collapsed (resolver context builders now delegate to the single domain implementation). To the user: one merge behavior across every source, not three subtly different ones.
    - **Cursor-based incremental, never windowed re-reads** — the API's `after` cursor + checkpoint means each poll fetches only new plays; the ~50-play window makes missed data unrecoverable, so the checkpoint is the source of truth for "where we left off."
    - **First-poll calibration against Last.fm** — pin the API's `played_at` start-vs-end semantics empirically before the projection trusts the 30s tolerance for `spotify_api` pairs; until calibrated, `spotify_api` pairs use the wide fallback tolerance via their `ChannelSpec`. If end-time semantics are confirmed, the correction ships as ledger-carried data read by the existing `normalized_start_time` seam (the importer stamps the derived shift from the payload's `track.duration_ms`, full plays only) — never a new branch in domain code, and never a synthetic `ms_played`: survivorship takes the first non-null `ms_played`, so a duration-as-listened-time stand-in would corrupt the user's listening-time stats the moment it wins a merge. Dropping the `tolerance_override` at calibration is already safe (the `max(..., default=0.0)` guard shipped with v0.10.0).

- [x] **Demand-Driven & Adaptive Polling**

    **Story**: The user's play counts are fresh at the moments they matter — opening mixd after a listening session, an agent reading plays over MCP, a 6am scheduled workflow filtering on "played today" — and the poller is quiet the rest of the time. A fixed hourly timer gets this exactly backwards: it wastes most polls on silence and can still be an hour stale at the moment of use.

    **Decisions**:
    - **Three demand triggers share one staleness-gated helper** — play-surface reads (web API + MCP tools) fire it *fire-and-forget* so reads never wait; the workflow executor *awaits* it (bounded timeout, run proceeds on expiry) when the graph contains play-history nodes, because a scheduled workflow is precisely where stale counts silently corrupt output and nobody is watching.
    - **Freshness gates on last-*polled*, never last-*play*** — the checkpoint's `last_timestamp` records the newest play seen, which goes stale whenever the user simply isn't listening; gating on it would fire a pointless poll on every page view of an idle account. A new `last_polled_at` is the gate: "when did we last check," not "when did they last listen."
    - **The coverage heartbeat decides per tick, not per schedule** — the schedule stays at a fixed base cadence and the sync target early-exits from backoff state persisted on the checkpoint (consecutive empty polls stretch the effective interval; any new plays or demand trigger snaps it back). Adaptivity lives in the target, so scheduler infrastructure is untouched.
    - **The backoff cap is redundancy-aware** — if Last.fm is connected and scrobbling, a missed window is recoverable (another live observer + the next GDPR export), so background polling may relax toward its slow cap; if `spotify_api` is the user's *only* live observer, the cap stays inside the window-turnover bound (~2h of dense listening), because then a missed poll really is permanent loss (PDR-001).
    - **Single-flight per user** — concurrent triggers (page focus + workflow start + heartbeat) collapse into one poll via a non-blocking pg advisory lock keyed `(user_id, "spotify:plays")`, the schedule repo's `try_acquire_poll_lock` pattern — DB-level because every replica serves demand triggers; losers no-op, and the cursor-based importer makes the winning poll cheap regardless.
    - **One execution path, three trigger sources (DRY)** — demand triggers and the scheduler heartbeat invoke the *same* shared sync-target runner, extracted from the scheduler's `_dispatch_sync` (where the `OperationRun` audit wrapping lives today), so every poll — scheduled or demand — produces the same audit row, updates the same checkpoint, and shows in the same run log and sync-status table. ### v0.10.2: Mapping Supersession & Resolution Event Log

**Goal**: Identity decisions become append-only — when a mapping changes, "we used to believe X" is preserved, rejections become memory instead of amnesia, and platform-asserted succession is representable — landing **before** the v0.11.x connectors mint mappings at scale.

**Context**: Today the mapping upsert overwrites method/confidence/evidence in place: flip-flops are invisible, and below-threshold rejections leave no record, so the same wrong candidate is re-fetched and re-rejected forever. Scheduled 2026-07-02 from the identity research ([memo D2](identity-resolution-design-space.md)); pulled forward from the former v1.0.0 Data Quality milestone (2026-07-16) because the supersession schema must represent platform-asserted succession (Apple catalog equivalents, Spotify relinking, Tidal `replacement`) distinctly from inferred re-matching *before* a second full connector exists — or v0.11.0 Apple forces a schema migration (memo §5.3). Re-sequenced 2026-07-27 to land **before** the first at-scale import (see Key Design Decisions), so the import mints mappings with supersession history from the start and the [v0.10.3 audit](#v0103-post-import-data-integrity-audit) reads an event log rather than reconstructing identity decisions from their surviving artifacts.

**What this unlocks**: v0.11.x connectors born with succession semantics (no migration); the change history the v0.14.0 Manual Mapping UI displays; the supersession substrate v1.1.0 cross-user identity's observation ledger requires; a negative cache that stops re-proposing rejected candidates on every import.

**Persona**: Curator-primary (trust in automated matching — bad flips become visible and reversible); Tinkerer secondary (an auditable identity ledger to query).

Pre-build research (2026-07-27, [memo §10](identity-resolution-design-space.md)) reshaped the design; the decisions below are its outcome, with rationale and sources in the addendum.

**Key Design Decisions**:
- **Supersede, never overwrite — with a five-value reason enum**: `id_dead | rematch | conflation | platform_superseded | manual`. Three registry precedents (Wikidata P2241, GLEIF, ROR) independently reproduce the split and contributed `conflation` ("points at a surviving sibling", the FM3b/FM2c class — 480 duplicate-canonical groups exist in prod today). `platform_superseded` is **MusicBrainz 301 merges only**.
- **Contextual substitution is never a supersession** — Spotify relinking, Apple equivalents, Tidal `replacement`, Deezer `alternative` all assert "in *this* market/storefront use Y", where the original stays valid (Spotify's own docs: mutations must use the original id). Retiring the incumbent would write-flap under multi-context users; substitutions are recorded as events with a `scope`, plus a secondary mapping where useful.
- **Every reader is live-by-default** (repository-level filter + partial live index) — Wikidata's answer to the half-aware-reader problem is that deprecated rows are "never used unless specifically requested"; mixd ships the same as the *default interface*, with `include_superseded` opt-in and the v0.4.9 integrity checks supersession-aware.
- **The event log is bitemporal-lite** — `recorded_at` (DB clock) + `decided_at` (matcher clock) + `evidence_as_of` (provider-snapshot freshness); without the split, the first bulk re-resolution stamps its wall clock over history and "what did we believe on date X" is unrecoverable. `matcher_version` is a **content hash of the full matcher config**, a provenance/validity key — never an auto-re-resolution trigger.
- **The negative cache is two mechanisms, not one** — *no-match* rows retry on backoff (ListenBrainz's shipped curve: 1d doubling to 32d cap, counter-free); *rejected pairs* are sticky cannot-link constraints keyed by matcher version + content hash so version bumps and metadata changes expire them (Reltio documents the accumulate-forever → silent-undermatching pathology; bias toward under-suppression per the RFC 2439→7196 history).
- **Debounce runs two clocks** — *absence* backs off (nothing to find yet); *suspicion* leans in (IABot re-checks a failing link faster, 7d→3d); one success resets immediately. Suspect state lives in events only; `id_dead` supersession is written when N=3 consecutive failures span ≥T days (T=9d starting point; measured Spotify transient band is seconds-to-minutes, so T may tighten on telemetry).
- **One write seam; mapping row and event commit in the same transaction** — the mapping table stays authoritative, the log is its trail (the event-sourcing literature's warning is against a beautiful log over disagreeing projections). All mutation sites route through it, including relink/unlink/set-primary/delete, not just the four FM6a writers.
- **This lands before the first at-scale import, not after** — the bulk Last.fm + GDPR import is where mappings are minted en masse and where flip-flops concentrate; with the in-place upsert still in the path, every identity decision that import makes is overwritten and unrecoverable. This buys *legibility*, not match accuracy (that was v0.8.18 + v0.10.0's casing fix). Accepted risk: the seam refactor touches the import path, so the import runs on fresh resolution code and is its own acceptance test.
- **No genesis backfill; fresh-prod policy applies** — pre-v0.10.2 mappings carry no events ("no event recorded" is an accepted, surfaced state). Prod restarts fresh at (or before) v1.0.0 ([policy](v1.0.x.md#v100-maturity-gate)), and 91% of existing confidences are hardcoded constants worth nothing to calibration.

#### Mapping Integrity Epics

- [x] **Supersession Schema**

    **Story**: When a mapping changes — an ID dies, a re-match finds better, a human overrides — the user wants "we used to believe X" preserved: today the upsert overwrites in place and the flip is invisible, so neither the user nor the system can tell a correction from a regression, and when a track's history suddenly looks wrong there is no way to answer "what changed, and when." Preserved history is what makes automated matching trustworthy: a bad flip becomes visible, attributable, and reversible instead of a silent mystery.

    **Decisions**:
    - **Scalar `superseded_by_id`, not an edge table** — N:1 merges work natively, no split-writer exists in mixd, and event evidence carries the full candidate array (Apple equivalents, MB no-redirect splits) so a future edge table can be backfilled if ever forced. `supersession_scope` (nullable = global) ships now — the one cheap column Apple would otherwise force by migration.
    - **True chain, no MusicBrainz-style path compression** — mixd's chain *is* the history (MB compresses because its redirect table is a lookup aid and its merges destroy the loser's payload — the cautionary precedent). Hot paths never walk: live lookups hit the partial index; chain walks are rare, depth-capped, and cycle-guarded. Edges between two already-superseded rows are legal (resurrection = a new row superseding the successor); superseded rows are retained forever.
    - **The live-rows default is implemented once, at the session layer** — `with_loader_criteria` in a `do_orm_execute` listener (the canonical soft-delete recipe), registered beside the existing RLS listener; `propagate_to_loaders` covers relationship loads. **Core statements are not covered** — a module-level `live_only()` clause is required in every Core `select()` touching mappings, enforced by a conformance test; the partial unique index is the hard write-side guard. One half-aware reader means a corrected mapping's ghost resurfacing in the user's library forever.
    - **Metadata drift never supersedes** (ROR's rule: name changes update the record; only identity changes create succession) — a re-verified-unchanged assertion touches freshness only, or every enrichment refresh grows the chain.
    - **Supersession writes respect the identity-map staleness rule** — Core-DML flips mixed with ORM reads in one session serve stale rows unless reads use `populate_existing`; v0.10.0's projection hit exactly this. The loader-criteria filter does not save you — it filters SQL, not the identity map.

    **Spec**:
    - Migration 044 (house style 040–043; DML bracketed `NO FORCE ROW LEVEL SECURITY`): `track_mappings` gains `superseded_by_id` (self-FK, `ON DELETE SET NULL`, **`DEFERRABLE INITIALLY DEFERRED`** — the write path references a not-yet-inserted successor; legal because the arbiter is the unique *index*, verified PG17), `superseded_at`, `supersession_reason` (varchar(32), enum in domain), `supersession_scope` (nullable), `next_verify_at` (nullable — the FM4a substrate: GLEIF's "lapsed" analog; no re-validation worker this milestone); CHECK: the three supersession columns move as a unit (`superseded_by_id` stays nullable — retirement with no successor)
    - Live-uniqueness moves to partial indexes: drop `uq_track_mappings_user_connector` → unique `(user_id, connector_track_id, connector_name) WHERE superseded_at IS NULL`; `uq_primary_mapping` gains `AND superseded_at IS NULL`; reader index `(user_id, track_id) WHERE superseded_at IS NULL`; `autovacuum_vacuum_scale_factor = 0.02` (supersession updates an indexed column — never HOT)
    - Write path `assert_mappings` (replaces destructive `bulk_upsert` for mappings): two statements, one transaction — `INSERT … ON CONFLICT (…) WHERE superseded_at IS NULL DO UPDATE` with the predicate restated (partial-index inference requires it), `EXCLUDED.id` = pre-generated uuid7 successor id, an `IS DISTINCT FROM` tuple deciding touch-freshness vs supersede; then plain-insert successors (`RETURNING superseded_by_id` discriminates); bounded retry on SQLSTATE 23505 (the post-supersession re-probe branch is undocumented internals)
    - Downgrade deletes superseded rows (cannot coexist with the restored full unique — documented as irreversible, 040-style)

    - **The queue lives on the server, not in the browser tab** — walking away is the whole point, and a client-side loop dies with the tab, a sleeping laptop, or a dropped connection, stranding the remaining files with no record of what was left to do.     - **One file at a time, by design** — v0.10.2.4's measurement put ~80% of import time in the per-track write path against Neon, so parallel files would contend for the same pool and race to create the same canonical tracks: concurrency buys contention, not throughput. ### v0.10.3: Post-Import Data Integrity Audit

**Goal**: After the first at-scale imports land on prod, an agent adversarially audits the resulting data — duplicate plays, missed merges, identity twins, dropped observations — and every finding becomes either a verified "clean" or a scheduled fix, before later cycles build features on top of the history.

**Context**: v0.10.0's convergence guarantees are proven by property tests and the manual acceptance run, but those exercise *fixtures*; the first at-scale import (full Last.fm history + fresh GDPR export, v0.10.0/v0.10.1's joint acceptance) is the first time the projection meets real data at volume — legacy quirks, encoding edge cases, and channel behaviors no fixture anticipated. The pre-ship deep review found (and fixed) several silent failure classes that would have been invisible without targeted queries (conflict-skipped phantom inserts, 1→N split overwrites, unowned >6h-`ms_played` groups, END-vs-START adoption misses); the honest assumption is that real data holds more such classes, not fewer. This audit runs once the user confirms the prod imports are done. Ordering decided 2026-07-27: v0.10.2 lands first, so the identity checks below read the resolution event log as primary evidence instead of inferring decisions from surviving artifacts — where a check can be answered from the log, prefer it and say so.

**What this unlocks**: trust in the history every later feature consumes (metrics, "loved but forgotten", v0.13.2 physical listens); a re-runnable audit harness that future imports and connectors (v0.11.0 Apple Music) are checked against; an enumerated defect list feeding the v0.10.2 identity work and the casing-fix residue.

**Persona**: Curator-primary (their history is the product; this is its acceptance at scale). Tinkerer secondary (the audit harness is a scriptable diagnostic surface).

**Key Design Decisions**:
- **The checklist below is a floor, not a ceiling — with a bound** — the implementing session's first task is to *expand* it: re-derive failure modes from the projection code, migrations 040–042, the [convergence findings](play-import-convergence-findings.md), and the v0.10.0 review history, then add checks this list missed. **Cap: ~10 new checks**, each read-only, each recorded in the findings doc with the failure mode it targets; anything costing more than a single query gets proposed to the user before it runs. Both failure modes are real — an audit that runs only the listed queries has failed its brief, and one that runs eighty unbudgeted ones has too.
- **Report-only, against a Neon branch of prod** — every check is read-only and runs on a copy-on-write branch (the CI pattern), never the prod primary; no mutation happens without a user-approved follow-up story or revision.
- **Every check is executable and re-runnable** — checks land as `diagnostic`-marked integration tests or a read-only script (`scripts/audit_play_integrity.py`), not one-off psql sessions, so the same audit re-runs after v0.10.1 polling, v0.11.0 Apple Music, or any future re-import.
- **Findings are quantified with exemplars** — each check reports pass/fail, the count, the query, and 3–5 exemplar rows; "some duplicates exist" is not a finding.

#### Audit Epics

- [ ] **Adversarial Data-Integrity Audit Run**

    **Story**: With real listening history on prod for the first time, the user wants proof the convergence machinery actually converged — no double-counted listens, no silently dropped scrobbles, no twin tracks splitting one song's history — delivered as a findings report they can read and act on.

    **Decisions**:
    - **Session-executed, adversarially framed** — attack each guarantee (idempotence, order-independence, one-play-per-listen, one-track-per-song) and try to construct queries that *falsify* it, not confirm it.
    - **Delegation policy: one investigator per check group, no verifiers** — groups A–E are independent and read-only, which is the shape fan-out actually pays for; cap at one subagent per group, and never spawn one to re-check another's findings. The session writes the findings doc itself, so the verdicts stay in one voice.
    - **Refuted-in-code scenarios still get data checks** — the review refuted several failure modes by code inspection (e.g. legacy `import_source` values, rebuild deleting history); the audit verifies the *data* agrees with the code-level argument, since prod is the first environment where the premises are tested.

    **Spec** — preliminary checklist (grouped; the session extends it, within the cap above):
    - **A. Duplicate plays**:
      - Cross-channel merge misses: same user+track pairs of plays within 180s whose `source_services` are disjoint singletons (`{spotify}` vs `{lastfm}`) — should have grouped; bucket by Δt (0–30s vs 30–180s) against the findings §3 pairing baselines
      - Legacy END-shift twins: pairs where `p2.played_at ≈ p1.played_at + p1.ms_played` (±2s), same track — a pre-v0.10 end-stamped row surviving beside its start-normalized sibling
      - Same-channel exact duplicates on `(user_id, track_id, service, played_at)` — must be zero post-migration-040
      - Over-merge check: merged plays whose members' normalized starts differ by >30s with `ms_played` present (tolerance violation), or with more members than registered channels
      - Re-import delta: repeat one already-imported source; assert zero row-count and zero content delta (the manual acceptance test, formalized as a harness check)
    - **B. Ledger ↔ canonical consistency**:
      - Canonical plays with zero `play_sources` membership (expect ≈0 after a rebuild)
      - Resolved `connector_plays` with no membership edge — dropped observations (probe especially rows with `ms_played` > 6h and rows at the projection range edges, the clamped/unowned classes)
      - `source_services` array vs actual membership-edge services mismatch
      - Rebuild idempotence on prod data: real rebuild, then `--dry-run` → all stats zero except unchanged (any persistent `groups_updated` churn = a non-convergent field, the `_differs`/write asymmetry class)
      - Import-reported projection stats vs actual row deltas for one observed import
    - **C. Track identity / mapping**:
      - Casing/normalization twins: canonical track pairs equal under `normalize_for_comparison` on artist+title — residue the v0.10.0 casing fix should have stopped growing
      - ISRC twins: same ISRC on >1 canonical track
      - Divergent-resolution plays: enumerate every play whose members resolved to different `track_id`s (the bridge's `resolution_divergence`) — each is a named identity defect for the v0.10.2 queue
      - Cross-service doppelgängers: single-service canonicals whose normalized identity matches a canonical mapped only to the other service
      - Tracks with plays but zero connector mappings; mappings referencing missing tracks
      - SEARCH_FALLBACK substitutions whose track duration is shorter than the user's longest completed listen of the dead id (median `trackdone` `ms_played` − 15s) — the retroactive detector for the v0.10.2.3 wrong-version class; also compare each substitution's artist similarity against the fallback floor introduced there
    - **D. Field sanity**:
      - `ms_played`: negative, > track `duration_ms` (with tolerance), > 6h (count the clamp class and eyeball exemplars)
      - `played_at`: future timestamps, pre-service-existence dates, systematic ±1h/±24h cluster offsets (timezone/DST bug signatures)
      - Context shape: multi-member plays carry `merged_from_<channel>` keys; sample-diff imported vs rebuilt context on a Neon branch (must be byte-identical — the single-builder guarantee)
      - Tenancy: every plays/ledger/membership row carries the expected `user_id` (the `'default'` mistenancy class); RLS-scoped counts equal raw counts
    - **E. Aggregate cross-checks**:
      - Per-day play counts vs external truth: Last.fm's own scrobble total, GDPR export row count net of documented filters (duration/incognito — reconcile the excluded counts too)
      - Overlap-window both-services rate vs the findings §3 ~82.7% pairing baseline; investigate windows that fall far below
      - Distribution smell tests: plays-per-day outliers, duplicate-heavy single days, `same_channel_collapsed` volume vs findings §7's 266-pair baseline
    - Deliverable: `docs/backlog/v0.10.3-audit-findings.md` — per-check verdict, query, counts, exemplars, plus every *new* check the session added and why; harness committed as re-runnable diagnostics. **Length budget**: one subsection per check, ≤3 exemplar rows, ≤120 words of prose each; no executive summary and no restated methodology section — the checklist above is the methodology

    **Tests**:
    - The audit harness IS the test surface: each check re-runnable via `diagnostic`-marked integration tests or the audit script against a database URL
    - (unit) any helper queries with nontrivial logic (e.g. END-shift pair detection) get fixture-backed unit coverage so the audit itself isn't wrong
