## What Epic C inherits (constraints, not history)

- **`user_id` is threaded through the import pipeline, not carried on params.** `BasePlayImporter._fetch_data` and `_handle_checkpoints` both take a required `user_id: str`. Keep this shape in the poll policy — it is what makes the checkpoint key impossible to get wrong.
- **Importer registry keys on `(service, ImportKind)`** (`ImportKind = Literal["file","api"]`, in `src/domain/repositories/play.py`). Resolver factories deliberately keep bare-service keys: the orchestrator types the factory as `Callable[[str], …]`, and a script plus a patched test double depend on that arity.
- **`SpotifyRecentImportParams(limit, force)`** — `force` ignores the stored cursor for one poll and re-reads the whole retained window. Exposed on the REST schema and the chat `import_data` tool.
- **The connector-scope gate is 409 `CONNECTOR_SCOPE_MISSING`** (`ConnectorScopeMissingError` + `require_connector_scopes(service, scopes)` in `deps.py`), not RFC 6750's 403 `insufficient_scope` — that status describes the *caller's* token, and here the caller is fine while the upstream grant is short. Reuse this dep for any further scope-gated route.
- **`build_play_context` dispatches on `ChannelSpec.context_builder`**, with `_generic_context` as the fallback for unregistered `(service, import_source)`. A new channel supplies its builder in the registry entry — there is no service if-chain to edit.
- **`import_spotify_recent` is in `_IMPORT_LIKE_TYPES`** (`routes/operation_runs.py`): it is a user-triggered import and belongs in the run log's default view. Epic C's `sync:*` poll runs deliberately stay out (dozens/day would drown it) and show under type=all.

## Gotchas (do not re-derive)

- **`import_source` MUST be `"spotify_api"`** — `ChannelSpec ("spotify","spotify_api")` is registered in `src/domain/matching/play_projection.py` (priority 1, `time_semantics="start"`, `tolerance_override=180s` pending calibration). `channel_for` raises on unknown pairs.
- **Checkpoints key on the mixd `user_id`** — non-negotiable: `sync_checkpoints` is FORCE-RLS'd on that column with a USING-only policy, so any other key is rejected on write *and* invisible on read, and importers read that as "never synced". The Last.fm importer keyed on the Last.fm username and its checkpoint never persisted once (fixed 2026-07-26). The constraint is documented on `CheckpointRepositoryProtocol`.
- **Asserting RLS needs more than `db_session`** — `metadata.create_all` creates no policies, and the testcontainer role is a superuser (superusers bypass even FORCE), so a naive test passes vacuously. `tests/integration/connectors/lastfm/test_lastfm_checkpoint_rls.py` applies the 007+011 DDL and connects as a `NOSUPERUSER NOBYPASSRLS` role; reuse that fixture, and keep its self-proving "the wrong key is rejected" test.
- **A xact-scoped advisory lock cannot guard the poll** — the importer commits per batch, releasing `pg_try_advisory_xact_lock` at the first internal commit. Single-flight is the checkpoint claim column (user-approved deviation from the backlog's advisory-lock wording; update the backlog Decision text at completion).
- **Scheduled syncs are currently mis-attributed** — `scheduler._dispatch_sync` omits `initiated_by`, so they land as `"manual"`. The runner extraction fixes this (pass `initiated_by="schedule"`).
- **The `Schedule` entity is deliberately daily/weekly-only** — the 30-min heartbeat needs the new `interval_minutes` cadence arm (user-approved).
- **`SYNC_DISPATCH` is a flat `dict[str, Callable[[str], Awaitable[object]]]`** — no decision-function concept exists; the descriptor rework introduces it.
- **`launch_background` is interface-layer** — the MCP/chat demand hook lives in application-layer `registry.py`, so demand fire-and-forget needs an application-local spawner (create_task + strong-ref set + done-callback), not an interface import.
- **No `users` table exists** (`user_settings` is preference KV) — the activity signal gets its own `user_activity` table.
- **Migration head is `042_play_sources`** — next is `043`; run `uv run alembic heads` first.

## Idle-compute constraint (added 2026-07-26 — read before C1)

The background-loop substrate Epic C builds on changed underneath this plan. Neon's compute suspends after **5 minutes with no query activity**, and on the Launch plan that timeout is fixed. The scheduler's 60s poll and the sweeper's 30s poll were keeping it awake 24/7, so both became demand-driven:

- **`SchedulerConfig.poll_interval_seconds` is gone**, replaced by `max_sleep_seconds` (default 6h). The loop now sleeps until `find_next_wake_at()` — the earlier of the next due fire time and the oldest claim's reap deadline — instead of polling. `grace_seconds` no longer derives from the poll interval; it is the fixed `SCHEDULE_GRACE_SECONDS = 120` in `scheduler.py`.
- **`run_periodic_background_loop` → `run_adaptive_background_loop`** (`periodic_loop.py`): the tick supplies its own next delay via `next_delay`, and an optional `wake_event` cuts a long sleep short. The event is cleared *before* each tick so a signal raised mid-tick is never lost.
- **Two new in-process signals.** `services/run_activity.py` (`track_run()`) gates the sweeper's cadence; `services/schedule_signal.py` (`notify_schedule_changed()`) wakes the scheduler when a write brings a fire time forward. Both are advisory — correctness still comes from the next DB read.

**What this means for Epic C:**

1. **The `interval_minutes` cadence arm (C1/C7) composes cleanly** — sleep-until-due handles a 30-minute heartbeat natively, and better than the old poll did (no up-to-60s drift). `compute_next_run`'s interval branch feeds `next_run_at`, which is exactly what `find_next_wake_at` reads. No scheduler-loop changes needed.
2. **Mind the duty cycle when picking backoff constants.** The C3 starting points (base 30 min; caps 2h sole-observer / 24h redundant) each imply a cost: at a 30-minute interval the compute is awake ~17% of the time, at 2h ~4%, at 24h ~0.3%. The adaptive stretch on empty polls is therefore a *cost* mechanism as well as a politeness one — worth saying so in the C3 docstring. The **5-minute `interval_minutes` floor is the pathological case** (100% duty cycle); it is allowed by the CHECK but should never be the play-poll default.
3. **`_dispatch_sync` is already wrapped in `track_run()`** — the wrap sits in `_process_one`, *above* the dispatch call, so the C5 refactor of `_dispatch_sync` into a thin adapter over `run_sync_target` inherits it without change. Don't add a second wrap inside the runner.
4. **The C8 activity middleware is fine as specced.** Its >5-minute monotonic throttle means an active user writes at most once per 5 minutes — and an active user is one the compute should be awake for anyway.
5. **`ensure_fresh_plays` demand triggers (C8) are the right shape** for this: they fire on reads a user actually made, so they add no idle cost. `spawn_ensure_fresh_plays`'s fire-and-forget task should still be short-lived — a task lingering in `idle in transaction` would pin the compute indefinitely (Neon counts that state as active).

**Pre-existing bug found and fixed while doing this work (2026-07-26).** The heartbeat ticker was started by whoever drove a run, and only the API path ever did — the CLI and the scheduler both omitted it. Their runs kept `heartbeat_at IS NULL`, and `list_stalled_runs` reaps any `running` row past the stale threshold without one, so a scheduled or CLI workflow lasting over a minute was marked `crashed` while it was still executing.

The ticker now lives inside `ExecuteWorkflowRunUseCase`, which takes a third injected dependency, `HeartbeatBumper` (`workflows/protocols.py`), alongside the two status updaters. `run_lifecycle.heartbeat_loop` is gone; `bump_heartbeat` remains as the concrete single-bump impl. **This changes a constructor signature C5 touches** — `run_scheduler_loop` / `run_scheduler_tick` / `_process_one` / `_dispatch_workflow` all thread `bump_heartbeat` through, and the lifespan injects it. Making it required is deliberate: it is the forcing function that stops a fourth driver from forgetting.

One behaviour to preserve: a run that never yields to the event loop still records no heartbeat, so the sweeper's `cold-start hang` classification (`heartbeat_at IS NULL`) keeps working. Both halves are pinned by tests in `test_workflow_runs.py::TestExecuteWorkflowRunHeartbeat`.

## Context

The GDPR export delivers depth but arrives weeks late (the user's export stops 2025-02-28); Last.fm is live but identity-weak. Epic B added Spotify's recently-played API as a fresh, strong-identity channel, but it only runs when someone asks. Missed polls are permanent data loss (~50-play API window, [PDR-001](../decisions/PDR-001-data-ownership-model.md)), so Epic C adds both halves of the answer: a coverage heartbeat so plays don't age out between sessions, and demand-pulled freshness so counts are current at the moments they're consumed.

## Decisions resolved during planning (incl. deviations from backlog text)

1. **Heartbeat cadence = new `interval_minutes` arm on `schedules`** (user-delegated; criteria: least hacky/most debuggable/best UX). Nullable `interval_minutes` (CHECK 5–1440, exclusive with `day_of_week`); claim/release/reaper machinery untouched. Poller stays a plain sync-target schedule row with all existing visibility.
2. **Single-flight = atomic claim column on `sync_checkpoints` (`poll_claimed_at` + 15-min TTL), not an advisory lock** (user-confirmed). The conditional-upsert claim fuses staleness gate + claim into one atomic statement. **Update the backlog Decision text** at completion.
3. **`sync:{target}` operation_type** for all runner-produced runs (clean break from `scheduled_sync:{target}`; only scheduler.py references the old string). Poll runs stay OUT of `_IMPORT_LIKE_TYPES` (visible under type=all with an `initiated_by` badge).
4. **Bug fix folded in:** `_dispatch_sync` `initiated_by="schedule"` (see Gotchas).
5. **Redundancy signal = recent Last.fm scrobble** (`("lastfm","plays")` checkpoint `last_timestamp` within 7d), not token presence — token-present-but-silent degrades safely to the tighter sole-observer cap. Note this signal only became trustworthy with the Last.fm checkpoint fix; before it, that timestamp was always absent.
