# v0.13.x: Completing the Collection

For strategic overview, see the [planning overview](README.md).

## User Workflow Context

The foundations (v0.11.x) and the entities (v0.12.x) converge: Apple Music and Tidal graduate from bones to full peer connectors, the physical collection catalogued on Discogs finally lands in the library as ownership records on real albums, and manual listens close the last hole in the canonical history — the vinyl play that no service observes. After this cycle, the collection is *complete*: every service the user touches, every format they own, every listen they log.

The cycle then closes the loop from history back to the present: with both streaming services at parity, mixd can show what is playing *right now* and let the user tag it in the moment — the judgment happens while the song plays, not later from memory in a library page.

Persona view (from the [alignment table](README.md#persona-alignment)): the **Weekly Curator** gets the full reclamation story — streaming, physical, and manual history unified, plus tagging that happens in the listening session; the **Tinkerer** gets the re-resolution machinery, collection import, and Tidal playlist CRUD to script; the **Casual** listener gets "connect Apple Music" and "connect Tidal" at parity with Spotify.

Cross-cutting contract (stated once — per-epic Specs reference it): every new use case this cycle must be classified in the chat-tool parity registry (`src/application/tools/registry.py`) — CI (`tests/unit/application/tools/test_registry_parity.py`) fails on any unclassified use case. Reads get a `ToolSpec` or an explicit classification; mutations additionally get two-phase confirmation wiring like the existing `*_write` dispatchers.

### v0.13.0: Apple Music Integration

**Goal**: Apple Music reaches parity as a library connector — likes, playlists, catalog search — and the plays v0.11.0 deliberately deferred converge into the canonical history.

**Context**: The v0.11.0 bones (auth, client, ISRC-only resolution, play channel) have been accruing observations; the v0.12.x entity work shipped the alias-aware comparator and album context that full resolution needs. This milestone finishes the connector: the library surface (Apple has no "love" API — Add to Library is the like analogue) and the designed exit for every deferred observation.

**What this unlocks**: "like on Spotify, appears in Apple Music library" cross-service sync; Apple playlists in workflows; the deferred Apple plays finally resolved and projected — the payoff of ingest-early/resolve-conservatively.

**Persona**: Curator-primary (full Apple parity); Casual secondary (Apple Music users become first-class citizens).

**Key Design Decisions**:
- **No `LoveTrackConnector`** — Apple has no love API; `LikedTrackConnector` maps to library additions, and pretending otherwise would fabricate a signal the service doesn't have.
- **Re-resolution is the ledger's designed exit, not a repair** — v0.11.0 recorded fallback candidates unresolved on purpose; resolving them now with the full matcher and replaying the projection (`mixd plays rebuild`) is the plan completing, with every decision logged in the v0.10.2 event log with matcher version.

#### Substrate Epics (cycle-wide)

- [ ] **Connector Reconnect-State Unification**

    **Story**: The user whose grant dies mid-cycle wants the same "Reconnect [Account Name]" framing on every connector — today only Apple gets it. Spotify's compare-and-delete on `invalid_grant` means the very next status probe after the one that catches the dead refresh renders "Connect" like the account was never linked; Tidal's dead-grant path does the same, immediately, losing the account name entirely. A credential aging out should never look like the user has to start over.

    **Decisions**:
    - **Keep the row, clear only the refresh token, stamp the marker** — mirrors Apple's already-shipped shape (`extra_data["reauth_required"]`, three shapes shipped in v0.11.x — see its completion notes) rather than compare-and-delete, because deleting the row is what erases `account_name` and collapses the connection to "never connected" after one probe cycle. Spotify and Tidal move onto Apple's shape; Apple's is not renegotiated.
    - **One read derives `needs_reauth` for every connector** — `_shared/connector_status.py`'s three status functions each independently decide dead-grant meaning today (`get_spotify_status` catches `SpotifyReauthRequiredError` from a just-completed silent refresh; `get_apple_music_status` reads the `extra_data` marker; `get_tidal_status` infers from `not has_refresh and expires_at <= time.time()` with no marker at all). Converging them onto one shared predicate is what makes "unify" more than a rename.

    **Spec**:
    - `_shared/connector_status.py`'s three shapes converge: every dead-grant detection point stamps `extra_data["reauth_required"]`, and all three status functions read that one marker instead of three different signals
    - `SpotifyTokenManager._refresh_token` (`spotify/auth.py`) and `TidalTokenManager._post_refresh` (`tidal/auth.py`) stop calling `storage.delete_token(...)` on `invalid_grant`; both clear `refresh_token` only and stamp the marker, preserving `account_name` and `extra_data` (both already carry these fields forward on a successful refresh — see Extract the Dead-Grant Ritual below for the shared helper)
    - Web (`GET /connectors`) and CLI status render the reconnect affordance with the account name intact for all three connectors, not just Apple

    **Tests**:
    - (unit) a dead grant on each of Spotify/Apple/Tidal stamps the same marker and derives `needs_reauth` via one shared predicate
    - (integration) the connector card and CLI status keep showing the account name across the reconnect transition — no "Connect" flash for a connector that was previously linked

    Effort: M | Dependencies: Connector Auth-State Fidelity (v0.11.x — the `reauth_required` marker and `needs_reauth` derivation shipped there; see its completion notes) | Status: Not Started

- [ ] **Extract the Dead-Grant Ritual**

    **Story**: A rider on the unification above — `spotify/auth.py` and `tidal/auth.py` duplicate detect-`invalid_grant` → compare-and-delete → clear-cache → typed-raise, plus the `scope`/`extra_data`/`account_name` carry-forward, down to identical log strings. Tidal is the second refresh-token connector to copy the block verbatim; a third would copy it again without this extraction.

    **Decisions**:
    - **Extract now — two implementors already meet the rule of three's spirit** — the same forcing-point test v0.13.4's Connector-Name Extensibility epic applies to dispatch sites applies here to a duplicated ritual: Spotify and Tidal are byte-identical apart from connector name, and the unification epic above is about to touch both call sites anyway, making this the cheap moment to fold them into one implementation instead of two.

    **Spec**:
    - `_shared/token_refresh.py`: `discard_dead_grant(storage, service, user_id, current_token)` — the keep-row/clear-refresh-token/stamp-marker sequence from Connector Reconnect-State Unification, replacing both connectors' compare-and-delete blocks
    - `carry_forward(current_token, new_token_fields)` — the `extra_data`/`account_name` preservation logic duplicated in `SpotifyTokenManager._refresh_token` and `TidalTokenManager._post_refresh`
    - `spotify/auth.py` and `tidal/auth.py` call the shared helpers; connector-specific exception types (`SpotifyReauthRequiredError`, `TidalReauthRequiredError`) still raise at each call site — only the shared mechanics move
    - Wants its own test pass: the shared module is tested once, not per-connector

    **Tests**:
    - (unit) `discard_dead_grant` clears only `refresh_token`, preserves every other stored field, and stamps the marker
    - (unit) `carry_forward` preserves `extra_data`/`account_name` across a refresh response that omits them
    - (regression) Spotify's and Tidal's existing dead-grant tests pass unchanged against the shared helpers

    Effort: S | Dependencies: Connector Reconnect-State Unification | Status: Not Started

#### Hygiene

- [ ] **Collapse the `_run_*` Importer Skeletons**

    **Story**: The Tinkerer scripting a new importer, and whoever debugs the next one, both want one place to fix the ingest→resolve pipeline instead of six — `import_play_history.py` repeats build-params → importer → orchestrator → two-phase → log/except almost verbatim across `_run_lastfm_recent`, `_run_lastfm_incremental`, `_run_lastfm_full_history`, `_run_spotify_file`, `_run_spotify_recent`, and `_run_apple_recent`. A bug fixed in one skeleton silently survives in the other five until someone hits the same symptom twice — importer reliability is one skeleton, not six.

    **Spec**:
    - `_run_two_phase(command, uow, progress_emitter, *, params, label)` — one method folding the shared shape (`_create_service_importer` + `_create_play_import_orchestrator` + `orchestrator.import_plays_two_phase` + the `try`/`except`/log pair) each of the six skeletons currently repeats (~210 lines collapsing to ~80, per the original estimate)
    - Per-mode callers narrow to building their own `params` object (`LastfmImportParams`, `SpotifyImportParams`, `SpotifyRecentImportParams`, `AppleRecentImportParams`) and a label string, then delegate
    - Mode-specific pre-checks stay with their caller, not the shared method: `_run_lastfm_full_history`'s unconfirmed-cancel early return, `_run_spotify_file`'s missing-`file_path` `ValueError`
    - Picked up in this milestone ahead of the next new mode landing on the file, so the collapse happens once rather than being copied an eighth time

    **Tests**:
    - (unit) existing per-mode tests pass unchanged against the collapsed skeleton — behavior-neutral refactor
    - (unit) a new mode wired through `_run_two_phase` needs only a `params` object and a label, no new `try`/`except`

    Effort: S | Dependencies: None | Status: Not Started

- [ ] **Extract the ISRC-Minting Inward-Resolver Base**

    **Story**: Whoever fixes the next ISRC-collision or mapping-claim bug wants one place to fix it — `apple_music/inward_resolver.py` and `tidal/inward_resolver.py` are ~68% line-identical after normalizing connector nouns, ~330 lines apiece, and Spotify holds a third copy of the same shape. A fix to the suspect-ISRC arm lands three times or not at all, and the fifth connector copies it a fourth.

    **Decisions**:
    - **This milestone is the trigger, not an arbitrary slot** — v0.11.x's quality pass deliberately left the duplication alone because the two sides genuinely diverge today: Tidal dedupes planned writes by current id (two dead ids can share one `replacement`), Apple does not, because its `playParams.catalogId` dual-mapping path is dormant until the library surfaces this milestone adds. Extracting before that lands would mean a shared base carrying a Tidal-only branch. Once Apple's dual mapping activates here, both sides need the fan-in dedup and the extraction is mechanical.
    - **Extract the minting layer, not the whole resolver** — Spotify's fallback search and relinking are genuinely its own; only the ISRC-minting spine is shared.

    **Spec**:
    - `IsrcMintingResolver` in `_shared/inward_track_resolver.py`, holding the eight members that match across connectors: `_IsrcCollisionReview`, a generic `PlannedWrite[PayloadT]` (with `requested_id_is_stale` / `creates_canonical`), `_plan_write`'s reuse / suspect-collision / plain-create arms, `_persist_writes` (+ its `_log_failed_write` closure), `_canonical_payload`'s evolve-out of a suspect ISRC, `_persist_writes_bulk`, `_mapping_batch` (including the `claimed`/`claim()` dedupe), and `_record_substitutions`
    - Connectors supply four hooks: `to_track(payload)`, `service_metadata(payload)`, `duration_ms(payload)`, `SUBSTITUTION_DETECTION`
    - Apple and Tidal migrate first; Spotify's ISRC arm follows only if it lands byte-identical — its search-fallback and relinking paths stay put either way
    - The fan-in dedup (writes keyed by current id, one collision review and one canonical create per identity) becomes the shared behavior, since Apple needs it once dual mapping is live

    **Tests**:
    - (unit) existing per-connector resolver suites pass unchanged — behavior-neutral for Tidal, and for Apple only where dual mapping was previously unreachable
    - (unit) two dead ids sharing one successor fan in to a single canonical, on every connector implementing the base

- [ ] **ConnectorCard Connect-Flow Registry**

    **Story**: The user connecting any service wants `ConnectorCard` to already know how — today it branches on `auth_method` in four places (`isBrowserBridge`, `isTokenAuth`, the `onConnect` ternary, the token-dialog JSX) and hardcodes the Apple MusicKit hook and the Discogs token dialog inline, so a new connect flow means editing the shared card instead of registering one. `device_code` is already listed as connectable in `isConnectable()` (`lib/connectors.ts`) with no card branch at all — the first connector to use it would hit this gap live.

    **Decisions**:
    - **A `connectFlows` registry, not a fifth branch** — `Record<ConnectorAuthMethod, {useConnect, Dialog?}>` replaces the `isBrowserBridge`/`isTokenAuth` conditionals; `ConnectorCard` looks up its flow by `auth_method` instead of naming Apple and Discogs in branches.
    - **`DiscogsTokenDialog` generalizes into the registry's token form** — its scaffold (open state, PUT-token mutation, validation) is already connector-agnostic apart from the endpoint; parameterizing it into a generic token dialog is the registry's second entry, proving the shape works for more than one flow before a third connector needs it.
    - **`device_code` gets a real registry slot** — closes the gap between "connectable" and "has a flow" before any connector actually emits it, instead of after.

    **Spec**:
    - `web/src/components/shared/ConnectorCard.tsx`: replace the `isBrowserBridge`/`isTokenAuth`/`onConnect` ternary with a `connectFlows[connector.auth_method]` lookup; `oauth` keeps the existing `useConnectorAuth` redirect as its default entry
    - `DiscogsTokenDialog` → generic `TokenConnectDialog` taking the connector name + endpoint as props; Discogs becomes its first caller, not its only one
    - Apple's `useAppleMusicConnect` prewarm behavior (MusicKit setup ahead of the click) moves into its registry entry's `useConnect` hook unchanged

    **Tests**:
    - (component) each registered auth method renders its flow via the registry lookup, not a hardcoded branch — Apple's browser_bridge and Discogs's token flow both pass their existing test suites through the new registry
    - (unit) a `device_code` entry (fixture connector) renders its dialog without any `ConnectorCard.tsx` edit

### v0.13.1: Physical Media & Discogs

**Goal**: Track which albums the user owns and on which media. Discogs as the primary source for physical release metadata — pressings, formats, labels, catalog numbers.

**Context**: Your music identity isn't just streaming — it's the vinyl on your shelf, the CDs in your car, the albums you've purchased digitally. Discogs has 15M+ releases with rich physical media metadata (format, label, catalog number, country, pressing notes). Importing a user's Discogs collection instantly populates "what I own and in what format."

**What this unlocks**: the physical half of the library — ownership records that v0.13.2's manual listens and future collection features build on.

**Persona**: Curator-primary (the record collector's data reclamation); Tinkerer secondary (a new connector to explore). Casual: not served — physical collections are a Curator concern.

**Key Design Decisions**:
- **Release ≠ Album**: An album (release group) can have many releases (pressings). "OK Computer" is one album; the 1997 UK vinyl, 2008 Japanese CD, and 2017 OKNOTOK remaster are three releases.
- **Discogs as primary physical source**: MusicBrainz has releases too, but Discogs has stronger collector community data (condition, notes, marketplace). Start with Discogs; MusicBrainz release data can supplement later.
- **Read-only initially**: Import from Discogs, don't write back. User manages their Discogs collection on Discogs.

### v0.13.2: Manual Listens

**Goal**: Record physical album listens — "I put this record on at 3pm" — scrobble to Last.fm and store as canonical plays in mixd.

**Context**: When you listen to a vinyl record, that listening event is invisible to your digital history. Mixd should let you log it: pick the album, enter when you started, and the system figures out the per-track timestamps from track order and durations. The plays become part of your canonical history — indistinguishable from streaming plays in workflows and metrics.

**What this unlocks**: complete listening history — physical plays join the canonical record, so "loved but forgotten" workflows and play metrics stop under-counting vinyl listeners.

**Persona**: Curator-primary (the vinyl listener whose history has holes); Tinkerer secondary (CLI + scripting surface). Casual: not served by this milestone.

**Key Design Decisions**:
- **Album-level input, track-level output**: User says "I listened to this album starting at 3pm." System calculates per-track timestamps and creates individual `TrackPlay` records. Each track gets its own play entry because that's what Last.fm expects and what mixd's play history model requires.
- **Optional Last.fm scrobble**: User chooses whether to also scrobble to Last.fm or keep it mixd-only. Some people want to keep physical and digital scrobbles separate.
- **Retroactive and real-time**: Support both "I listened yesterday at 3pm" and "I'm listening right now."

#### Listen Infrastructure Epics

- [ ] **Last.fm Scrobble API**

    **Story**: Sending play events to Last.fm is the foundation for physical listens reaching the user's scrobble history.

    **Decisions**:

    - Batch: up to 50 scrobbles per request via indexed params (`artist[0]`, `track[0]`, `timestamp[0]`, etc.)
    - Requires same session key auth as `track.love` (already implemented)

- [ ] **Album Listen Calculator**

    **Story**: Converting "album listen at 3pm" into individual track plays with correct timestamps is the core logic of manual listens — and it must be right, because it writes permanent history.

    **Decisions**:
    - **Missing durations: use any connector-known duration; otherwise skip that track's scrobble but keep the mixd play** (timestamp = previous track's end) — fabricating durations would corrupt permanent history, and dropping the play entirely would under-count, the exact defect this milestone fixes.
    - **"Listening right now" means "just finished", not "starting now"** — the real-time input is listen *end* = now, timestamps computed backward; computing forward from a now-start would write future-dated plays that Last.fm rejects and mixd can't honestly claim happened.

    **Spec**:
    - Pure domain function: `calculate_listen_timestamps(tracks: list[Track], start_time: datetime) -> list[tuple[Track, datetime]]`
    - Track N+1 starts at: start_time + sum(duration of tracks 1..N)
    - Handle multi-disc albums: disc order → track order (already modeled in `album_tracks` via disc_number + track_number)
    - Pure function, no side effects — testable in isolation

    **Tests**:
    - (unit) timestamp arithmetic incl. multi-disc ordering and missing-duration handling

- [ ] **Record Album Listen Use Case**

    **Spec**:

### v0.13.3: Now Playing

**Goal**: With mixd open in a tab, the user sees what they are listening to right now and can tag it, rate it, or like it in one click — no searching for the track they just heard.

**Context**: Tagging is a v0.7.2 feature the user has to *remember* to do later, from a library page, against a track they have to find again. The moment of judgment ("this is a late-night one") happens while the song is playing and is gone by the time they open the library. This milestone puts the playing track permanently on screen with the tag/rate/like actions attached to it. Scope is Spotify and Apple Music only — Last.fm's `nowplaying` scrobble flag is a viable third source but carries no position, no service track id, and depends on a scrobbler being configured, so it stays out.

The two services reach the same surface by opposite mechanisms, and that asymmetry drives the design:

- **Spotify can be observed and commanded remotely.** `GET /me/player/currently-playing` reports whatever the user is playing on any device — phone, desktop app, another browser — and the `/me/player/*` write endpoints steer that same device. mixd watches and remote-controls; the user listens wherever they already do.
- **Apple Music can be neither.** There is no now-playing endpoint in the Apple Music API, and `SystemMusicPlayer` (the only API that can see the Music app) is native-only. The single path from a browser is **MusicKit JS**, which makes the mixd tab itself an Apple Music player. For Apple, "what's playing" is only knowable — and only controllable — because mixd is what's playing it.

The user should not be able to tell which is which. Both render the same bar with the same controls.

**What this unlocks**: tagging at the moment of judgment rather than from memory; mixd as a place you keep open while listening rather than a place you visit to do maintenance. Also the first in-app audio playback, which later surfaces (auditioning a workflow's output, previewing a playlist diff) can build on.

**Persona**: Curator-primary (the tag/rate ritual moves into the listening session where the judgment actually happens); Casual secondary (a now-playing bar with working controls is the most self-explanatory surface in the app); Tinkerer tertiary (a real Apple player plus a Spotify remote-control surface to script against).

**Key Design Decisions**:
- **Two sources, two mechanisms, one surface** — Spotify is polled, Apple is played in-tab, and the bar renders whichever is live without the user picking a mode. Forcing one mechanism onto both services would mean either dropping Apple (unobservable) or making the user listen inside mixd for Spotify too (a downgrade from their own client).
- **Actions write to mixd, never to the service** — tag, preference, and like all land locally, and the existing `sync_likes.py` machinery propagates outward on its own schedule. Writing straight through would need `user-library-modify` on Spotify and a direct Add-to-Library call on Apple, for an action the user experiences as instant either way; keeping it local also means the bar works identically for both services instead of having two failure modes.
- **The bar never writes plays** — Spotify plays already arrive via the v0.10.1 recently-played poller, and Apple plays via the v0.11.0 channel (MusicKit playback registers in Apple's own history, so it comes back through the normal channel). A now-playing observation would be a third writer of events the ledger already receives, and the projection would be reconciling mixd against itself.
- **Both services get transport controls** — a bar that can skip an Apple track but only watch a Spotify one teaches the user that the controls are unreliable, which is worse than not having them. Play/pause/next/previous/seek work identically on both, and the mechanism difference (mixd's own player vs. a remote command to whatever device the user is on) stays invisible.
- **Where a service refuses, say so in the control, not in a toast** — Spotify transport is Premium-only and needs an active device; both refusals are detectable and are rendered as a disabled control with a reason, never as a control that appears to work and then fails. The alternative — hiding controls per account tier — makes the bar a different shape for different users with no explanation.
- **An unrecognized track still renders** — the bar shows title/artist/art from the service payload immediately and resolves to a canonical track lazily, on the user's first action. Blocking the display on resolution would make the bar flicker empty for exactly the new music most worth tagging.

**Already in place**: tagging (v0.7.2 — `tag_track.py`, `untag_track.py`), preferences (v0.7.0 — `set_track_preference.py`), Apple auth + MusicKit user token (v0.11.0), Apple track resolution (v0.13.0), Spotify inward resolution (`spotify/inward_resolver.py`), adaptive-poll precedent (v0.10.1), missing-scope re-consent (`missing_scopes()` in `spotify/auth.py`, `CONNECTOR_SCOPE_MISSING` at `interface/api/middleware.py:252`).

#### Now Playing Epics

- [ ] **Spotify Now-Playing & Transport**

    **Story**: The user listening on their phone or the Spotify desktop app sees that track appear in mixd within a few seconds, and can pause or skip it from the bar — without changing anything about how they listen.

    **Decisions**:
    - **Read and control ship together** — they are one grant, one client surface, and one user expectation; splitting them would land a bar whose controls arrive a release later than the track they sit under.
    - **Two scopes, no more** — `user-read-currently-playing` carries `item`, `is_playing`, and `progress_ms` (everything the bar renders) and `user-modify-playback-state` covers every transport action. `user-read-playback-state` is still excluded: it would add device and shuffle/repeat state that nothing here displays, and Premium/device refusals are detectable without it.
    - **Detect Premium from the refusal, not from the profile** — a 403 carrying `reason: PREMIUM_REQUIRED` tells us what `GET /me`'s `product` field would, without the `user-read-private` scope and without reading the user's account details to decide whether to enable a button.
    - **Poll only while someone is watching** — the surface is a live view, not an ingest path, so polling is bound to a mounted, visible tab and stops on `visibilitychange`. A background poller would burn rate limit producing state no one reads.

    **Spec**:
    - Add `"user-read-currently-playing"` and `"user-modify-playback-state"` to `SPOTIFY_SCOPES` (`src/infrastructure/connectors/spotify/auth.py`). Existing tokens lack both — `missing_scopes()` already drives the re-consent prompt; the bar must render a "reconnect Spotify" state rather than an error when either is absent.
    - Read: client method on `SpotifyAPIClient` → `GET /me/player/currently-playing`; Pydantic model in `spotify/models.py` per the boundary-validation rule. Note the two empty responses: **204 No Content** (nothing playing) and a payload with `item: null` (private session / ad) — both mean "nothing to show", neither is an error.
    - Transport: `PUT /me/player/play`, `PUT /me/player/pause`, `POST /me/player/next`, `POST /me/player/previous`, `PUT /me/player/seek`. All return **204 with no body** on success — the new state is only observable on the next read.
    - Two refusals to model as first-class states, not errors: **403 `PREMIUM_REQUIRED`** (free account — controls disabled for the session, reason surfaced) and **404 `NO_ACTIVE_DEVICE`** (nothing to command — controls disabled until a device appears).
    - `GET /api/v1/now-playing/spotify` + `POST /api/v1/now-playing/spotify/{action}`. Poll cadence starting point (revisit): ~5s while playing, ~30s while paused, stop when hidden. The client interpolates `progress_ms` between polls so the position advances smoothly without raising poll rate.
    - **A transport action forces an immediate re-read** rather than waiting for the next tick — Spotify applies the command asynchronously, so the bar reconciles against the service instead of trusting its own optimistic guess. Debounce rapid skips; the poll interval is not a rate limit.
    - Parity (file-header contract): read → `ToolSpec`; transport actions are mutations, but **exempt from two-phase confirmation** — they are self-evident and instantly reversible by the user, and a confirm dialog on "skip" would make the control useless. Record the exemption in the classification.

    **Tests**:
    - (integration, mocked transport) playing payload parses; 204 and `item: null` both yield "nothing playing", not an exception
    - (integration, mocked transport) each transport action issues the right verb and path; 204-no-body is a success, not a parse failure
    - (integration, mocked transport) 403 `PREMIUM_REQUIRED` and 404 `NO_ACTIVE_DEVICE` surface as typed disabled-states, not generic connector errors
    - (use case, mock UoW) already-mapped track returns its canonical id; unmapped track returns the service payload with a null canonical id
    - (unit) a token without either scope produces the re-consent signal, not a 500
    - (unit) `test_registry_parity.py` stays green with the confirmation exemption recorded

    Effort: M | Dependencies: None (v0.13.0 not required — Spotify path is independent) | Status: Not Started

- [ ] **Apple Music Web Playback (MusicKit JS)**

    **Story**: The Apple Music subscriber plays music inside mixd — full tracks, real transport controls — because that is the only way a browser can know what an Apple Music listener is hearing.

    **Decisions**:
    - **The mixd tab becomes the player, and that is the feature, not a workaround** — Apple exposes no now-playing read at all, so an observe-only design would silently exclude every Apple user from this milestone.
    - **Event-driven, not polled** — MusicKit emits `nowPlayingItemDidChange` and `playbackStateDidChange`, so the Apple path has zero polling cost and zero latency, unlike the Spotify path.
    - **Playback is not a play observation** — a MusicKit session registers in the user's Apple Music history and returns through the v0.11.0 channel, so the player writes nothing to the ledger itself.

    **Spec**:
    - Developer token endpoint: server-side ES256 JWT signed with the MusicKit private key (the Apple Developer Program membership and key are the v0.11.0 prerequisite). **Max 6-month TTL — mint short-lived and refresh; never ship a long-lived token to the client.**
    - MusicKit JS v3 loaded in the web app; `music.authorize()` yields the Music User Token, reusing the v0.11.0 per-user credential storage rather than a second Apple credential path; the `Referrer-Policy` requirement is already satisfied globally by `SecurityHeadersMiddleware` (the v0.11.x bridge route it originated on is gone).
    - Transport: play / pause / next / previous / seek, plus queue-from-a-mixd-track. Standard controls are an Apple terms requirement on any MusicKit surface, not a nice-to-have.
    - Non-subscribers get 30-second previews from Apple regardless of what we do — detect via the authorization result and label the surface honestly instead of appearing broken.
    - **DRM requires a secure context**: a page served over plain HTTP from anything other than `localhost` silently degrades to previews rather than erroring. Production (HTTPS) and `localhost` dev are fine; a Vite dev server reached over a LAN IP is not — document this in `docs/development.md`, because the symptom looks like a broken integration.

    **Tests**:
    - (unit) developer-token minting: correct ES256 claims, TTL within Apple's 6-month ceiling, key never serialized into a response
    - (component, mocked MusicKit) `nowPlayingItemDidChange` updates the surface; transport actions dispatch; unauthorized state renders the connect prompt
    - (manual) full-track playback as a subscriber; preview-only state as a non-subscriber

    Effort: L | Dependencies: v0.11.0 (Apple auth + MusicKit user token) | Status: Not Started

- [ ] **Now Playing Surface**

    **Story**: The user keeps mixd open in a tab and always knows what is playing, on phone or desktop, without the bar getting in the way of the page they are actually using.

    **Decisions**:
    - **Live source wins, ties break to Apple** — Apple can only be playing if mixd itself is playing it, which is a stronger signal of present attention than a poll of a Spotify session that may be on a device in another room.
    - **The bar is chrome, not a page** — it docks persistently so tagging never costs a navigation, which is the entire point of the milestone.

- [ ] **Act on the Playing Track**

    **Story**: The user hears something worth remembering and tags it, rates it, or likes it right then — the judgment lands on the track while the track is still playing, which is the only moment they reliably have the opinion.

    **Decisions**:
    - **Resolve on first action, not on display** — a track the user has never played before has no mapping yet, and that is exactly the track most worth tagging. The user's intent to act is what justifies minting the canonical track; displaying it does not.

    **Spec**:
