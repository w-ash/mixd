## Confirmed defects

### C1 · `spotify_api` stamps play END, not start — FAIL

Median `lastfm − api` offset **−205.8s** against a **219.7s** median track duration; 69 of 110 pairs beyond the fallback tolerance; an independent sign test found **90/90** nearest pairs one-directional with zero exceptions.

`CHANNEL_SPECS[("spotify","spotify_api")]` declares `time_semantics="start"`, so no shift is applied and every API observation lands a track-length away from the export's and Last.fm's view of the same listen. The `tolerance_override=180.0` was the hedge against exactly this uncertainty and the median offset exceeds it, so it fails for any track over ~3 minutes. The existing `normalized_start_time` seam cannot correct it either: all 113 `spotify_api` rows carry `ms_played = NULL`.

This is the calibration [v0.10.1](v0.10.x.md#v0101-continuous-play-polling) deferred ("calibrated, not assumed"), now answered. That epic also pre-specifies the fix: the importer stamps the derived shift from the payload's `track.duration_ms`, full plays only, read through the existing seam — never a synthetic `ms_played`, which would corrupt listening-time stats the moment it won a merge.

Query: `scripts/audit_play_integrity.py --check spotify_api_lastfm_delta`.

### C2 · Spotify's export contains jittered duplicate rows the ledger cannot collapse — FAIL (upstream)

**283 near-duplicate pairs in the source JSON**: same `spotify_track_uri`, byte-identical `ms_played`, timestamps 1–2s apart. Confirmed by scanning `data/imports/Streaming_History_Audio_*.json` directly, so the origin is upstream, not the import path.

The ledger already collapses **3,807 exact duplicates** through the ON CONFLICT key, and `_collapse_same_channel` collapses same-instant pairs — but both require an identical `played_at`, so the jittered class survives as ~250–470 double-counted canonical plays. It is also the cause of the single physically-impossible day (2018-09-04, 25.17h of playback in 24h).

Two genuine plays of one track cannot begin one second apart with identical `ms_played`, so a small same-channel tolerance closes this safely.

| a_id | b_id | played_at | ms_played | Δt |
|---|---|---|---|---|
| `019fe8ec-363e…a9ad` | `019fe8ec-363e…0447` | 2021-09-19 23:10:30.532 | 216468 | ~1s |
| `019fe8ec-8ed6…7564` | `019fe8ec-8ed6…2fdd` | 2021-11-26 02:10:15.591 | 314409 | ~1s |
| `019fe8fd-f5e8…c963` | `019fe8fd-f5e8…33c5` | 2022-01-13 05:57:23.073 | 242927 | ~1s |

### C3 · 20 of the user's plays depend on another tenant's tracks — FAIL

24 of the real user's `connector_plays` resolve to `default`-owned tracks; **20 `track_plays` carry a `default`-owned `track_id`** (20 distinct tracks). The FK is `ON DELETE CASCADE`, so purging the mistenanted `default` rows — routine housekeeping until now — would silently delete 20 of the user's plays.

The import *reused* tracks created by the early mistenanted poller run rather than creating its own. That is match-before-create working correctly, except across a tenant boundary — which `tracks`' `FORCE ROW LEVEL SECURITY` policy should have prevented. The likely mechanism is that production connects as `neondb_owner`, recorded in the [pre-import baseline](play-import-convergence-findings.md) as holding `BYPASSRLS`; **if so, RLS is currently enforcing nothing in production**. Confirm before any cleanup, and re-own or duplicate those 20 tracks first.

Compounding: **485 of the 486 `default` tracks have a normalization-equal twin under the real user**, so any cleanup that dedups globally, or any path that drops the `user_id` predicate, merges the two identity graphs.

### C4 · Canonical reuse keyed on ISRC splits releases into twins — FAIL

**55 groups / 110 canonicals** share normalized artist+title but differ by ISRC. Reuse checks ISRC, which a remaster never shares with its original (the [v0.10.2.12](v0.10.x.md#post-deploy-revisions) finding), so each release spawns its own canonical even though the normalized columns already collide — the dedup key is simply not consulted. Normalization coverage is total (0 NULL of 56,776), so this is policy, not a data gap. The newest cohort post-dates the v0.10.0 casing fix, so it is still growing.

- `bonobo` / `ibrik mixed` — identical title **and** duration (245,733ms), ISRC `GBEXH1900012` vs `USA2B2056087`, 34 plays vs 1
- `ame` / `line solomun remix kristians vote` — "Kristian‘s Vote" (448,200ms) vs "Kristian's Vote" (216,000ms)
- `avalanches` / `oh the sunn` — "Oh the Sunn!" (235,400) vs "Oh The Sunn!" (138,213)

### C5 · A whole listening session was never submitted to the resolver — ~~FAIL~~ REFUTED

**Not a defect.** The population is exactly **28 distinct ids / 83 rows, every one `incognito_mode: true`** — private-session plays, which the resolver partitions out *before* resolution by design, so no `resolution_events` row is ever written for them. Verified directly.

The block looked like a lost session because a private listening session *is* contiguous: in the source JSON the incognito flag occupies one unbroken run of 120 records, and the non-private tracks immediately before and after it both resolved normally. The population also reproduces across three separate import runs — including one that completed with zero errors, which alone rules out chunk loss.

What C5 actually diagnoses is **the observability gap that made a designed exclusion look like data loss**: production cannot distinguish "skipped by policy" from "failed to identify", because migration `050` (`exclusion_reason`) is unapplied *and* the deployed build predates the `_CARRIED_RESOLUTION_METRICS` carry-through that puts `incognito_excluded` in the run record. Both fixes exist in the repo; neither is live. Closing either one closes this finding.

### C6 · 30 resolutions succeeded and failed to persist — FAIL (replayable)

30 URIs carry a `write_failed` event, so the track was identified and the *write* was refused. Transient by construction and healed by a re-import, since write-back matches on the ledger natural key. Largest: `69gRFGOWY9OMpFJgFol1u0` (Daddy Yankee, 9 plays, 2015-01-01); several Boards of Canada and Tusks tracks at 2–3 plays each.

### C7 · Six listens resolved to two canonicals each — FAIL, and it is C3

Six `track_plays` have contributing ledger rows that resolved to *different* `track_id`s; the merged row silently picks one. All six are recent (2026-07-28 → 08-03).

**Correction to this document's first pass**, which claimed the two canonicals differ because their titles differ between services. They do not. Measured: in all six, the pair is **the same recording — one ISRC, one title, one duration** — and the split is a **tenant boundary**, real user vs `default`, on every single one. C7 is therefore a strict subset of **C3**, not an identity-matching problem.

| track_play | owners | distinct ISRCs | title |
|---|---|---|---|
| `019fc3ef-6ea5…` | real, `default` | 1 | Burnin’ |
| `019fc3ef-721e…9d35ed9e5` | real, `default` | 1 | Mesa Redonda |
| `019fc880-199b…` | real, `default` | 1 | Low and Slow - Original Mix |

The remedy is C3's — stop `DEFAULT_USER_ID` leaking into the poller, confirm the `BYPASSRLS` hypothesis, re-own the mistenanted tracks. Cross-service identity matching would be the *wrong* fix here, and the reuse fix's user-scoped lookups correctly refuse to make it.

### C8 · The event log records a supersession whose artifact was hard-deleted — FAIL (minor)

`resolution_events` holds **5** supersession events against **4** surviving superseded mappings. Event `019fe42a-a8d4…` names superseding mapping `019fe2e7-4ade-7329-bbbc-c14df7681437`, which no longer exists in `track_mappings` — deleted outright rather than tombstoned. The append-only log is the more complete record, which is the outcome v0.10.2 intended, but a hard delete on an append-only substrate should not be reachable.

## Refuted

**The `trackdone` wrong-version hypothesis.** 2,632 plays end `trackdone` yet report under 50% of their track's duration, which looked like mappings pointing at longer versions (the v0.10.2.3 class). Testing it killed it: the anomaly rate is **flat across match methods** — `direct` (exact id, substitution impossible) is 2.30%, *worse* than the relink path `direct_import_stale_id` at 1.58%, where a substitution defect would have to concentrate. The canonical's `duration_ms` also equals the connector track's to one decimal in every method, so there is no longer version to point at. 188 of the 2,632 have `ms_played = 0` and 386 are under five seconds — a Spotify logging artifact.

Corroborating: **zero `search_fallback` mappings exist in production at all.** The v0.10.2.3 guard rejected 796 candidates at decision time (title similarity clustering at 0.60 against a 0.9 threshold) and never wrote them. The class was prevented, not merely survived.

The real residue in that direction is the inverse and much smaller: **614 plays with `ms_played` > 110% of duration**, concentrated in `canonical_reuse` (348 plays / 180 tracks) — consistent with C4.

## Corrections to earlier counts

**Genuine resolution failures: 51 rows across 30 tracks**, under the classification migration `050` will write. A broader predicate (any play with no mapping at all, live or dead) yields 144 rows / 67 tracks; the 93-row difference is entirely **incognito plays, which are never submitted for resolution by design** and so are not failures. 51 + 93 = 144, exact.

**The listen threshold discards 37.7% of ledger rows, not 37.7% of listens.** 84% of discards never reached 15% of their track (45,210 under 5%). The decision-relevant slice is far smaller — see below.

## Open decision: the listen threshold

`should_include_spotify_play` counts a play at ≥4 minutes, or ≥50% of a track under 8 minutes. Against this corpus (79,659 resolved-then-discarded plays):

| Alternative | Would admit | Share of discards |
|---|---|---|
| 30s absolute floor (Spotify's own stream definition) | 15,422 | 19.4% |
| ≥25% of track | 6,916 | 8.7% |
| ≥33% of track | 4,085 | 5.1% |

`play_threshold_ms` / `play_threshold_percentage` are settings, and the projection is replayable, so a change is a config edit plus `mixd plays rebuild` — no re-import, fully reversible. Report-only: where the threshold belongs is the user's call.

Re-run: `--check listen_threshold_discards`.

## Could not determine

- **Whether the 6h normalization clamp behaves correctly.** No prod row exceeds 63 minutes of `ms_played`, so the check passes vacuously.
- **Whether the 28 never-attempted URIs are dead, relinked, or live.** Distinguishing them needs a Spotify API call, outside a read-only audit.
- **Whether C5's skipped session was an import-boundary bug or a resolver crash.** No per-row error column, no log entry — absence of evidence.
- **The true-pair denominator for cross-channel pairing rates.** Measured 61.7% at 30s (n=162) for lastfm↔export against the findings §3 ~82.7% baseline, but the denominator includes genuinely off-Spotify listening, so this is a weak signal rather than a regression.
- **`exclusion_reason` breakdown from the database.** Migration `050` is written and tested but unapplied to production, so the too-short / incognito / failure split above is derived rather than read.
